# P7 面试与最终交付物代码说明

## 阶段结论

P7 的“代码交付面”已经完成：有统一 benchmark CLI、可恢复 Job、WebUI 评测中心、README 受控结果区块和架构图。真实模型结果是否能公开是外部证据问题，必须等 Langfuse Score 回读、人工审核和去敏 export 完成。

## 1. 从命令到结果的链路

```text
CLI / WebUI
  -> EvaluationCatalog 读取 suite manifest
  -> EvaluationRequest 校验 profile/benchmark/Skill/model/runtime
  -> EvaluationJobService 持久化 Job 并启动 worker
  -> benchmark.py prepare/estimate/run
  -> Agent + evaluator + Langfuse Dataset Run
  -> job progress / case checkpoint / remote score readback
  -> resume、case rerun 或 export
  -> benchmarks/exports/<run-id> + README 受控区块
```

CLI 和 WebUI 共享 catalog、Job store、结果 reader 和失败分类；WebUI 不是另一套评测实现。

## 2. Catalog：把可选项变成可验证数据

`nanobot/evaluations/catalog.py` 从 `benchmarks/suites/<suite-id>/manifest.yaml` 生成 suite payload，列出：

- benchmark id 和兼容的 profile；
- Skill、模型 preset、Runtime profile；
- adapter 能力、外部资产和 LibreOffice readiness；
- 不可用项的结构化 reason，而不是让前端自己猜。

`EvaluationRequest` 在进入 worker 前校验 suite、profile、sample、模型和 Skill 组合。CI profile 不需要远端凭据；office smoke/release 必须通过 Langfuse、资产、许可证和 token preflight。

## 3. Job 与断点

`EvaluationJobStore` 将 job、request、阶段、PID、进度、case 结果和错误写入 `~/.cache/nanobot/benchmarks/jobs/`。`EvaluationJobService` 提供：

- 全局 single active run，避免两个 worker 写同一个远端 Run；
- `cancel` 保留终态，不会被 worker 的迟到事件重新改成 running；
- `resume` 复用同一稳定 Dataset Run 名，只执行未完成 case；
- `case rerun` 只选定一个已完成 job 的 case，并生成新的 attempt；
- terminal job 和私有 checkpoint 删除，活动 Job 删除直接拒绝。

worker 读取进度 JSONL 的 offset，增量 upsert case。case identity 同时包含 benchmark、Skill、模型和 case id；历史投影只保留最新 terminal attempt，避免 UI 统计把 resume/rerun 重复计算。

本地 Job 汇总详情与多个 Langfuse Dataset Run 合并时使用同一四元 case identity；远端 case 投影显式保留 `model_preset`，避免两个模型的同一 case 相互覆盖成重复详情。

删除采用后台异步清理时，`LangfuseEvaluationReader` 不清空全量历史缓存，只移除目标 Run，并用 tombstone 过滤并发旧刷新；因此前端立即移除目标行后，其他本地或远端结果不会在下一次轮询中短暂消失。

## 4. Benchmark CLI 的四个边界

| 命令 | 代码责任 | 不能做什么 |
| --- | --- | --- |
| `prepare` | 固定 revision、资产 digest、constraints、benchmark venv、LibreOffice 和 Dataset | 运行 Agent 或下载 latest |
| `estimate` | 输出样本数、模型/Judge 输入输出 token 估算 | 把估算写成真实 usage |
| `run` | 调用 Agent、evaluator、checkpoint、Langfuse Experiment 和 Score | 忽略 preflight 或复用错误 fingerprint |
| `export` | 读取完成且审核齐全的 Run，生成去敏快照和 README 区块 | 手工填分数、导出未审核 Run |

`run` 的每个 case 都有独立 workspace、trace、source digest 和 checkpoint；模型异常只写失败状态，不能生成可复用的 completed checkpoint。远端 item 只有必需 local score、`mybot_score` 和人工审核都齐全时才会被 resume 复用。

## 5. WebUI Evaluation Center

`webui/ws_http.py` 提供 `/api/evaluations/*` 路由：catalog、readiness、runs、cases、submit、resume、cancel、delete 和 Langfuse 结果 deep link。HTTP 层只做 token/请求解析和 off-loop 调度，业务状态由 `EvaluationJobService` 和 `LangfuseEvaluationReader` 维护。

`EvaluationCenter.tsx` 的主要交互是：

1. 读取 catalog，默认选择第一个可用 suite/profile；
2. 选择 benchmark、Skill、model preset、runtime profile 和 sample；
3. readiness 不满足时禁用提交并展示 reason；
4. 展示阶段进度、成功/失败/待审核 case、token/latency/score 摘要；
5. case 详情的 Variant 只显示实际变化的对比维度，模型对比显示真实模型标识，不重复 benchmark/Skill 常量；
6. 失败项可展开主因和并发信号，Resume 与 case rerun 通过明确的按钮触发；
7. Score、Judge reasoning、Trace 详情和人工审核跳转 Langfuse，不在页面复制。

这使 UI 能服务日常操作，但不会把云端评测真相变成另一份容易漂移的前端状态。

## 6. 结果导出与 README

`export_run()` 先验证：

- Experiment 已结束，且每个 item 有 `output_present` 和所需 evaluator score；
- 远端 required score 名称被规范成 `mybot_score`，兼容 Langfuse v3 score API；
- Annotation Queue item 全部具备 `mybot-human-review`；
- run 的 metadata、Git SHA、profile、模型、Skill、evaluator revision 完整。

通过后才写 `benchmarks/exports/<run-id>.json/.md`，并由 `_update_readme_benchmark_block()` 替换受控标记区块。原始 trace、Office 文件、密钥和不可上传的媒体不进入 export。任何检查失败都停止导出，禁止用旧结果或 estimate 冒充新结果。

## 7. 失败可解释性

`evaluations/failures.py` 将 worker 输出归类为配置、资产、模型 relay、timeout、网络、Langfuse score missing 或 unknown，并保留同时发生的 signal。UI 因此能区分“需要修配置”“可以 Resume”“应该创建新 Retry Job”，而不是只显示一个 exit code。

Case 已完整执行时，Langfuse Score 回读延迟属于远端最终一致状态，不再归类为 Job 失败：本地 Case
显示 `completed + pending`，score ingestion queue flush 超时也允许 Job 进入 `awaiting_review`。只有同步
Score 上传失败、Case 缺失、OTEL flush 等真正破坏结果完整性的异常才终止 Job；最终 export 仍会重新
校验所有必需 Score，不能发布尚未落库的结果。

同一规则也用于旧 Job 的只读兼容投影：只有全部 Case completed 且失败主因仅为 Score 延迟时才从
历史 `failed` 显示为 `awaiting_review`，不会覆盖真实 Case 失败。

## 8. 当前状态与边界

- `ci` 是无 Key、无网络的确定性入口；真实 Office benchmark 需要外部 Langfuse、资产、许可和 Judge。
- WebUI 只显示本地 Job 投影；Langfuse 是 Trace、Score、Dataset Run 和人工审核唯一真相源。
- OCB 自有 Judge 结果必须标记 `Mybot evaluation`，不能称官方可比。
- README 的真实数字只能由 export 更新；没有完整审核 Run 时必须显示“外部证据待配置”。
- P7 不引入独立 Demo、视频或答辩稿生成器。

## 2026-08-11：readiness 缺失与脱敏状态解耦

评测中心不再在 profile 尚未 prepare 时同时声称 Dataset 已准备但内容被脱敏。`Profile has not been prepared` 表示本地 prepared 元数据缺失；`Prepared Dataset contains redacted content` 仅表示已有 prepared 元数据明确记录 `licensed_content_uploaded=false`。两者互斥，实际运行硬门不变。

## 2026-08-11：prepare 可观察下载恢复

评测中心的 prepare Job 现在展示正在执行的实际阶段。校验通过的本地 pinned source 可离线复用；OCB 官方 Hugging Face 源连接失败会在有界超时后自动切换镜像，单次网络请求仍快速超时，整批 release snapshot 则允许最多 2 小时完成正常的多 GB 传输；Adobe 官方转换使用显式连接/读取超时并只重试缺失文件，macOS 标准 Edge/Chrome/Chromium 安装会自动投影为 `CHROMIUM_PATH` 以支持 HTML 许可源；子进程优先尝试 IPv4 但保留 IPv6 回退，避免 release 的公共源下载在无路由 IPv6 上逐文件等待。固定 revision、工作树洁净、LICENSE digest、manifest digest、asset fingerprint 和 Langfuse Cloud 回读仍决定 prepare 是否成功。

官方 OCB URL 中部分 Akamai/CloudFront 站点会按 TLS 指纹拒绝普通 Python HTTP 客户端。外部 benchmark venv 固定使用 `curl_cffi==0.13.0`，prepare wrapper 只为 pinned 上游 downloader 的 GET 请求注入 Chrome 指纹；不改变来源 URL、许可内容、Adobe PDF Services 转换、文件校验或 prepared fingerprint 口径。

若 Chrome 指纹仍收到 403/503、非预期 HTML 或 HTTP/2 传输错误，wrapper 有界尝试 Safari、Firefox 和 HTTP/1.1。`pypdf==6.15.0` 仅移除空密码可解的 PDF 容器加密，再上传同一 Adobe 服务；不可解密或内容损坏仍 fail-closed。

普通来源优先继续使用 pinned downloader 的标准 `requests`；只有明确拦截或 TLS 错误才切换浏览器指纹。每个缺失资产在独立有界子进程中恢复，单文件原生异常不再中断整批，最终仍必须通过全部资产格式、digest、Dataset mapping 和 Langfuse Cloud 回读硬门。

Office release 页面和 Job 采用新的固定可用口径：原分层 255 候选中排除 41 个不可执行 Case，并固定追加排除任务/参考证据契约或稳定产出异常的 Case 0、4、7，不从全量池补位；选择项为 OCB 211，两个模型合计显示并执行 422。prepared metadata 保留候选数与 44 个排除身份，便于结果解释和复现；Job 续跑复用既有其余 211 条 DeepSeek 结果，仅补跑 Luna。

评测中心历史结果按模型拆行展示，不再把双模型 Job 压成一条混合记录。DeepSeek 与 Luna 分别显示自身进度、失败数、得分、用量与 Langfuse 链接；运行中 Luna 在 Dataset Run ID 尚未返回时也有本地模型行，模型行展开只显示对应模型的 Case。

该投影只覆盖实际 `run` Job；prepare Job 保持单一准备记录。WebSocket worker 进度更新与 HTTP 历史轮询采用字段合并，实时事件未携带模型投影时不会清空已显示的 DeepSeek/Luna 行。

### 高频追问

**为什么 resume 和 retry 要区分？**

Resume 代表同一输入/fingerprint 的断点续跑，应该复用已完成 case；Retry 是一次新的实验尝试，必须新建 Job/Run，避免把不同环境混成一条历史。

**为什么 WebUI 不显示完整 Trace？**

Trace/Score/Annotation 本来就由 Langfuse 管理；Mybot UI 只提供操作和摘要，减少重复实现、敏感内容复制和真相漂移。

**如何证明 README 数字可信？**

数字只能从已完成、Score 齐全、人工审核完成的 Dataset Run 通过 `export` 生成，快照记录 profile、模型、Skill、evaluator revision 和 Git SHA，流程上禁止手工修改结果区块。
