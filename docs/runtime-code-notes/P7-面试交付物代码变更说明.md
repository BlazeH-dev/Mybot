## 这一阶段解决什么问题

一个项目“代码很多”不等于“别人能理解并相信”。面试官或新协作者通常只有几分钟，会问：

- 这个项目到底解决什么问题？
- 哪些是 nanobot 原有，哪些是你二开的？
- 你说安全、可恢复、可评测，证据在哪里？
- 没有 API Key 能不能复现关键路径？
- benchmark 是真实模型结果还是 fake provider？
- demo 失败时有没有稳定兜底？

P7 的目标是把 P0-P8 的代码变成可复现、可核对、不过度宣传的交付物。

## P7 应怎样做，而不是只“美化文档”

### 1. 先做证据矩阵

建议维护：

| 主张 | 代码证据 | 测试证据 | 指标/演示证据 | 可否写简历 |
| --- | --- | --- | --- | --- |
| Default 命令有 OS sandbox | sandbox manager/launcher | real provider smoke | CI Bubblewrap | 可以 |
| approval 超时不放行 | interactions/approvals | deadline tests | metric baseline | 可以 |
| 通用 exactly-once | 无 | 无 | 无 | 不可以 |
| Research Skill 已完成 | 无 | 无 | 无 | 不可以 |
| 真模型多 Agent 更快 | 无真实矩阵 | fake only | deterministic fake report | 不可以 |

这张表能防止面试中过度宣传，也方便快速找到证据。

### 2. Demo 必须可脚本化

演示不要依赖模型临场“刚好调用正确工具”。关键治理路径应尽量使用：

- 固定 fixture。
- cassette/fake provider。
- 固定命令。
- 已知的 file conflict 注入步骤。
- 可重复的 kill/restart 流程。

真模型 Office 生成可以作为效果展示，但安全和恢复证明应有确定性兜底。

### 3. 区分三种数字

P7 展示指标时必须标注：

- 确定性测试数据。
- fake-provider 模拟数据。
- 真模型真实运行数据。

例如当前 Subagent 90ms vs 120ms 只能叫固定 fake-provider workload 结果，不能说“多 Agent 性能提升 25%”。

### 4. 架构图要显示控制点

建议最终图至少展示：

```text
WebUI / WebSocket
  -> AgentLoop / Session
  -> Context / SkillsLoader
  -> AgentRunner
  -> Policy Gate -> Interaction/Approval
  -> SandboxLauncher / OCC
  -> Tools / Skills / Subagents
  -> Artifact / Checkpoint
  -> Trace / Eval
```

并用颜色或注释区分 nanobot 原有骨架与 Mybot 新增模块。

## 面试主线应该怎样组织

### 30 秒版本

> Mybot 是我基于 nanobot v0.2.1 二开的个人 Agent Runtime。我先用固定 Office fixture 和两个独立 Office Skill 打通真实任务，再补了 typed Skill manifest、Seatbelt/Bubblewrap sandbox、allow/ask/deny Policy、可持久化 HITL、SHA-256 OCC、artifact lineage、hash-bound checkpoint、cassette/trace/eval，以及受控 Subagent。当前确定性基线是 5 cases、0 hard failures；Research、多模型真值矩阵和文件租约仍明确标为未完成。

### 3 分钟版本的结构

1. 为什么基于 nanobot：复用 AgentLoop/Runner/ToolRegistry/MessageBus，不重复造 Agent 骨架。
2. P0-P2：用 Office 建立真实垂直切片和 Skill 治理。
3. P3：权限、人工确认和文件并发安全。
4. P4：输入/产物追踪和诚实恢复语义。
5. P5：含 LLM 系统的确定性测试、trace 和硬门。
6. P8：多 Agent 的数量、权限、上下文和产物隔离。
7. 数据与边界：5 cases PASS；fake-provider 不是实际模型性能；P6/P7 仍有未完成项。

### 10 分钟版本的重点

重点深挖两条调用链：

- 高风险 tool call 怎样从 Policy 到 approval、typed resume、Sandbox 和 OCC。
- kill 后怎样通过 plan hash、state hash、artifact checksum 区分 completed/pending/uncertain。

这两条最能体现 Runtime 工程，而不是普通聊天 UI。

## 固定追问题库

### 为什么基于 nanobot，不用 LangChain/LangGraph？

项目需要的是在现有轻量 AgentLoop/Runner 上补安全、恢复和评测硬门，而不是复杂图编排。复用 nanobot 可以把精力放在差异化 Runtime；P8 也只扩展现有 SpawnTool/SubagentManager。

### 哪些是你自己做的？

应按代码证据回答：双 Office Skill/shared facts、typed manifest 和 catalog、OS sandbox manager/launcher、Policy/Interaction/Approval、OCC、Artifact/Checkpoint、Cassette/Trace/Eval、Subagent governance 和相关 WebUI 协议是 Mybot 二开主线。不要把 nanobot 原有 MessageBus、AgentLoop 基础骨架和全部工具说成从零自研。

### 如何防数字幻觉？

固定 expected metrics，确定性脚本从 Excel 计算 verified facts，DSL 用 fact id，validator 和 data consistency metric 检查引用，最终 Office 产物再做文件/OpenXML/视觉校验。

### 如何防 prompt injection？

不把安全押在模型识别率上。文档/网页是 untrusted content；真正副作用仍经过 hard boundary、Policy、approval、Sandbox、SSRF 和 OCC。红队看越权后果是否为零。

### checkpoint 为什么不是 exactly-once？

远端副作用可能成功但本地未持久化，Core 无法统一查询所有外部系统。completed 跳过、pending 可安全重试、uncertain 必须人工决定。

### 多 Agent 如何受控？

要求 active/hash-bound parent plan，最多 5 direct child，禁止嵌套，child restricted root、独立 FileStates、child-bound approval、父子 trace和显式取消/循环熔断；不使用父 Agent 猜测的 token/time/tool 工作量配额。
