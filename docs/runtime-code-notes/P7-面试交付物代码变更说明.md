## 2026-07-29 评测中心交付面

交付从“只能跳转 Langfuse”扩展为可控、可恢复的评测入口：侧边栏“评测”打开 `#/evaluations`，页面展示 `ci`、`office-smoke`、`office-release` readiness，支持选择 benchmark/Skill/model/runtime、估算 token、启动确认、队列、实时进度、Case 状态、历史 CLI/WebUI Run 和 Langfuse Dataset Run/Trace/Annotation Queue 链接。页面不提交人工分数、不复制完整 Trace 或 Judge reasoning；Langfuse 仍是分数与审核真相源。

实现边界为可信仓库代码而非 WebUI 动态执行：`benchmarks/suites/<suite-id>/manifest.yaml` 描述维度、profile、来源、许可和 evaluator，`adapter.py` 接入共享 Job Service。这样新增 Research Quality、Runtime Policy、Recovery 或代码生成 suite 时复用同一 UI 和 Job contract。

中断恢复使用“Resume”和“Retry”两个明确动作：Resume 在同一 Job 上增加 `resume_count/history`，复用稳定 Langfuse Dataset Run，页面显示已完成/剩余 Case；Retry 创建新 Job 从头执行。网关重启只把失联 worker 标为 `interrupted`，不会自动恢复付费调用，用户复核 token 与上传范围后手动 Resume。Agent 完成 Case 的私有 `0600` checkpoint 仅用于避免重复模型 token，不返回前端；Langfuse 仍是 Trace、Score 和审核真相源。

Office release 不再只有 PresentBench 可缩小样本。评测中心对当前选中的 OCB、OfficeBench、PresentBench 分别提供 25%/50%/全量三档（`255/509/1018`、`24/47/93`、`60/119/238`）；选择通过统一 `benchmark_samples` contract 进入 readiness、token 估算、持久化 Job 和 CLI。release 不直接截取 manifest 前 N 项，而是使用公开固定 seed `mybot-office-release-v1` 生成单一分层确定性序列：OCB 按 format+track、OfficeBench 按 task id、PresentBench 按 domain 分层，层内按 case id 哈希排序并按层规模成比例交错。由同一序列取前 N 可保证输入换序后选择不变、重复执行可复现、25% 严格包含于 50%，同时近似保持全量分层比例。非全量样本上传到带 `-strat-v1-n<数量>` 后缀的独立 Langfuse Dataset，既防止复用全量 Dataset 造成实际 token 超出估算，也避免与历史“顺序前 N”的 `-n<数量>` Dataset 混用；strategy/seed 同步写入 Run metadata。旧 `presentbench_sample` payload 仅作为历史 Job/旧客户端兼容入口。

| Benchmark | 证明范围 | 口径限制 |
| --- | --- | --- |
| OCB | DOCX/XLSX/PPTX 理解 | Langfuse Dataset + Terra Custom LLM-as-a-Judge，标记 `OCB/Mybot evaluation` |
| OfficeBench Office subset | Word/Excel 创建、读取、编辑和跨文件 | 原样运行官方确定性 evaluator，记录 `official_score` |
| PresentBench | PPT 生成、材料忠实度、内容和视觉质量 | Langfuse Dataset/media + Terra Custom LLM-as-a-Judge；视觉不支持时仅该维度本地 SDK evaluator fallback |

### 按 benchmark 固定 evaluator

1. OfficeBench Office subset：官方确定性 evaluator，`evaluation_source=officebench_official`，记录 `official_score`。
2. OCB：Langfuse Custom LLM-as-a-Judge 通过 OpenAI-compatible LLM Connection 调用 `gpt-5-6-terra`，`evaluation_source=langfuse_terra`，记录 `mybot_score`。
3. PresentBench：Langfuse Custom LLM-as-a-Judge + 必要 Annotation Queue；视觉媒体不支持时仅该维度由本地 SDK evaluator 计算，记录 `mybot_score`。
4. P5 Core Runtime hard gate、cassette 和红队仍作为独立回归证据，不计入 benchmark 分数。

OCB/PresentBench 不标记 `official-comparable`。P7 不采集业务对话量、满意度、CPU、内存和 GPU。只发布任务/benchmark 成功、LLM/tool 成功率与错误、P50/P95、Token、Agent steps、等待/恢复和所选 evaluator 分数；人工结果保存在 Langfuse Annotation Queue，三套 benchmark 不合成总分。

### Langfuse

计划使用随 Mybot 默认安装且锁定版本的后端 Python SDK，复用其 OTel 上下文、observation 生命周期、`propagate_attributes()`、`mask_otel_spans`、batch/retry/flush、Experiment Runner 和 Scores API，而不是安装 Skill、使用前端 JS/TS SDK发送主 Trace，或自建通用 `TraceEvent/TraceSink` 协议：

```text
Mybot semantic instrumentation
  -> Langfuse SDK / OpenTelemetry context
       -> Langfuse Japan Cloud
            -> Trace / Dataset / Experiment / Score / Annotation Queue
```

Mybot 仍拥有采集点、`mybot.*` 语义、字段 allowlist、Runtime 状态和必须访问本地文件的 task/evaluator；Langfuse 负责 Trace/Sessions、Datasets/Dataset Runs、Experiments、Scores、LLM-as-a-Judge、Code Evaluator、token/延迟 Dashboard、Annotation Queue 和失败下钻。它不替代 Runtime 状态和无 Key 本地硬门。

部署固定采用日本区 Langfuse Cloud，注册和 SDK endpoint 均为 `https://jp.cloud.langfuse.com`。账号、项目和 API Key 在日本区单独创建，不能把默认欧盟区账号当作可原地切换的同一环境。Cloud 模式不要求本机 Compose，也不要求下载 Redis、MinIO、ClickHouse 或 PostgreSQL。

启用 Cloud 后不持久双写生产 JSONL；Cloud 故障不会阻塞普通 Runtime，但不承诺离线 Trace 补传。`office-smoke/release` 必须通过日本区真实写入、flush、API 回读和 deep link smoke，否则 profile 失败。远程只接收脱敏 metadata；原始 Office 文件、完整正文、artifact、密钥和个人信息默认不上传。日本区属于跨境数据传输，真实公司或敏感数据在合规审查前保持 Cloud 关闭。

公开 benchmark 的人工审计使用 Langfuse Annotation Queue：smoke 12 个 case 全审，release 约 5% 分层抽样并额外全审高风险、异常、Terra 分歧和视觉 `unscored`。获许可的渲染图和 checklist 可上传；Score/comment/reviewer 直接保存在 Langfuse，私有 Office 内容不能进入该队列。

Mybot 不实现通用 Trace 查询、Dataset/Experiment CRUD、Score 分析、跨 run 图表或标注 UI。本地 benchmark CLI 与 WebUI 共同负责受限的 suite 选择、Job 启动、进度、取消、手动 Resume/Retry 和本机 checkpoint；Langfuse Dataset Run/Score/Annotation 仍是评估真相源，Git 只保存导出快照。

P5 Core 硬门在本地 pytest/CI 执行；OfficeBench 官方 evaluator、OpenXML/渲染检查作为 Langfuse `run_experiment()` 进程中的 SDK evaluator functions 执行并直接返回 Langfuse `Evaluation`。OCB/PresentBench 使用 Langfuse Custom LLM-as-a-Judge，不重复建设 Mybot Judge 或 Score 存储。

## 当前一键入口

```bash
nanobot benchmark prepare --profile office-smoke
nanobot benchmark prepare --profile office-release
nanobot benchmark estimate --profile office-release --model-preset gpt-5-6-luna
nanobot benchmark run --profile ci
nanobot benchmark run --profile office-smoke --model-preset gpt-5-6-luna
nanobot benchmark run --profile office-release --model-preset gpt-5-6-luna \
  --ocb-sample 255 --officebench-sample 24 --presentbench-sample 60
nanobot benchmark export --dataset-run <langfuse-dataset-run-id>
```

- `ci`：确定性 eval、cassette、代表性红队、报告重生和 adapter contract；无网络、无真实模型、不开 Langfuse。
- `office-smoke`：三套公开集各 4 个固定分层 case，共 12 个且全部审计；两个 Skill 跑相同任务。
- `office-release`：OCB、OfficeBench、PresentBench 均可在 full/50%/25% 三档中选择并使用独立 Langfuse Dataset/series，换档不混合分母；固定 seed 分层序列保证 25% 包含于 50%。

三套 adapter 共用一个独立 benchmark venv；`prepare` 固定最小精确 constraints、revision/SHA/license、外部数据和 LibreOffice 版本，`run` 不临时下载。fingerprint 写入 Langfuse Dataset/Experiment metadata；Mybot 只保存可恢复 Job 的脱敏编排状态，不保存可编辑 Score。运行前估算并核对 token 规模。

release 顺序固定为 `prepare office-release -> estimate office-release -> run office-release`：prepare 缓存 OCB/OfficeBench release 数据和 PresentBench 三档候选资产，estimate 只读已准备数据，run 只消费选定 manifest。smoke prepare 不能替代 release prepare。

输出必须区分：

```text
benchmarks/runtime/   deterministic/fake-provider
benchmarks/office/    true-model public benchmark
benchmarks/exports/   从 Langfuse Dataset Run 导出的去敏快照
```

Langfuse Dataset/Experiment metadata 固定记录 benchmark revision、`evaluation_source`、git SHA/dirty、Skill id/digest、Luna/Terra preset、OfficeCLI/LibreOffice version/SHA、constraints、Judge/evaluator、Token、延迟、tool success、Agent steps、artifact hash 和 trace id。原始数据、完整 trace、渲染图和大体积 Office 文件不提交 Git。

报告同时给出 `supported/total`、`passed/total`、`passed/supported`，unsupported 的 token/耗时单列。分数下降由 Langfuse Dashboard/CI regression gate 展示或阻断；`export` 只有在 Dataset Run 完成且 Annotation Queue 审核齐全时才更新 README 受控区块。

Mybot WebUI 提供独立评测中心和受限 Job 状态机，但不提供人工评分按钮、Trace 详情、Experiment 编辑、Score 管理或跨 run Dashboard；这些仍在 Langfuse UI 查看，README/结果快照提供日本区 deep link。

## 操作者配置与发布顺序

精确配置值和命令维护在 `docs/plans/runtime-steps/P5-trace-eval.md` 的“P5.1 用户配置与真实运行步骤”，代码说明只记录与实现强绑定的事实：

1. `providers.openai.apiKey/apiBase` 只供 Luna Agent 使用；Langfuse Project Public/Secret Key 只供 SDK 写日本区 Cloud；Terra API Key/Base URL/model 只放 Langfuse LLM Connection。三者不是同一类凭据。
2. `captureContent=false` 时先运行 redacted prepare，验证 `_cloud_smoke()` 的 write -> flush -> API readback -> deep link。只有公开数据许可和跨境上传审查完成后，才临时设为 `true` 并传 `--allow-licensed-content`。
3. `prepare` 要求稳定版 `soffice` 绝对路径和精确版本输出；当前机器锁定 `/Applications/LibreOffice.app/Contents/MacOS/soffice` 与 `LibreOffice 26.2.4.2 0229ac93fcf0d7cbc6376066c6f35021cef002dc`，Codex runtime 的 LibreOfficeDev 不能作为 release gate。`estimate` 只按 Agent/Judge input/output 统计预计 token。
4. Langfuse 必须有两个独立 Judge filter：OCB 与 PresentBench；model 是 `gpt-5.6-terra`，Score 名精确为 `mybot_score`，sampling 100%，不作用于 OfficeBench。PresentBench rubric/media 未真实进入 Judge 时保持 `unscored`，不得伪造 Score。
5. 一个 smoke 命令产生六个 Dataset Run、六个 Queue 和 24 traces。OCB/PresentBench 等待 `mybot_score`，OfficeBench 等待 `official_score`；六个 Queue 的全部 item 都要写 `mybot-human-review` 并标记完成。
6. `export` 一次只处理一个 Dataset Run，检查 item、机器 Score、人工 Score、Queue 和 deep link。六个 Run 应分别留档；README 受控区块展示最后一次成功导出的 Run，禁止手工绕过。
7. 导出后恢复 `captureContent=false`，不需要普通 Cloud Trace 时同时恢复 `enabled=false`，并重启已运行 gateway。smoke 全闭环后才允许 release。

任一步缺失时，P7 状态仍是“代码完成、外部证据待配置”，README 保留“尚未发布”。

## 面试主线

> Mybot 先用 deterministic fixture 和 cassette 解决含 LLM 系统不可重复的问题，再用 Langfuse Dataset/Experiment 测 OCB、OfficeBench Office subset 和 PresentBench。OfficeBench 在 Experiment Runner 进程中调用官方 evaluator；OCB/PresentBench 使用 Langfuse Terra LLM-as-a-Judge，人工审核使用 Annotation Queue。Mybot 负责 Agent/Office 执行、本地硬门和可恢复 Job 编排，Langfuse 负责 Trace、Experiment、Score、Dashboard 和审核，让 OfficeCLI 与 OfficePython 在同一 Dataset 上比较覆盖、质量、token 和步骤数。
