- 数字来自确定性 fixture、fake provider、真模型还是人工审计？

## 尚未实现的交付闭环

### OfficePython

当前代码仍是 `office-automation` 窄工作流。后续 P1.1 将其改名为展示名 `OfficePython`、Skill id `office-python`，使用 `python-docx/lxml/openpyxl/python-pptx` 提供通用 `inspect/query/create/apply/validate/render`；旧 DSL 迁移到 weekly-report recipe。

在迁移代码、manifest、测试、配置和历史 id 兼容完成前，P7 不得把 `OfficePython` 写成已实现能力。

### 公开 benchmark

首批固定三套：

| Benchmark | 证明范围 | 口径限制 |
| --- | --- | --- |
| OCB | DOCX/XLSX/PPTX 理解 | 使用公开 revision 与 assertion evaluator |
| OfficeBench Office subset | Word/Excel 创建、读取、编辑和跨文件 | 只选 Word/Excel 单应用及 Word+Excel；结果写 `OfficeBench-Office/Mybot adapter`，不能冒充官方总体分 |
| PresentBench | PPT 生成、材料忠实度、内容和视觉质量 | 官方 rubric；非官方 Judge 标记 compatible |

SpreadsheetBench Verified 暂列选做，用于未来高级 Excel 深度验证。三套结果不合成总分。

### 三层评估

1. 确定性 hard gate：数字、文件、OpenXML、artifact、Policy、OCC、HITL、恢复和安全后果。
2. LLM Judge：被测 Agent 固定 `gpt-5-6-luna`，日常 Judge 使用独立 `gpt-5-6-sol`；记录 Judge/prompt 版本、成本和理由。
3. 人工 audit：100% 审计高风险异常及 hard/Judge 冲突，首次基线和发布版本对普通结果抽样约 5%。

P7 不采集业务对话量、满意度、CPU、内存和 GPU。只发布任务/benchmark 成功、LLM/tool 成功率与错误、P50/P95、Token/成本、Agent steps、等待/恢复和评估 score。hard failure 不能被 Judge 分数覆盖。

### Langfuse

计划使用后端 Python SDK实现可选 `LangfuseTraceSink`，而不是安装 Skill 或使用前端 JS/TS SDK发送主 Trace：

```text
Mybot TraceHook
  -> JsonlTraceSink（默认、脱敏、离线可用）
  -> LangfuseTraceSink（可选）
```

Mybot 仍拥有 task、Policy、Interaction、artifact、checkpoint 和 child 语义；Langfuse 负责开发者 Trace、Datasets、Experiments、Scores 和失败下钻，不是 Runtime 状态源，也不替代公开 benchmark evaluator。

部署固定采用日本区 Langfuse Cloud，注册和 SDK endpoint 均为 `https://jp.cloud.langfuse.com`。账号、项目和 API Key 在日本区单独创建，不能把默认欧盟区账号当作可原地切换的同一环境。Cloud 模式不要求本机 Compose，也不要求下载 Redis、MinIO、ClickHouse 或 PostgreSQL。

实现仍必须支持默认 JSONL、sink 故障降级和 `nanobot observability sync`，因此 Cloud 故障不会阻塞日常 Mybot。远程只接收脱敏 metadata；原始 Office 文件、完整正文、artifact、密钥和个人信息默认不上传。日本区属于跨境数据传输，真实公司或敏感数据在合规审查前保持 sink 关闭。

## 计划中的一键入口

```bash
nanobot benchmark run --profile ci
nanobot benchmark run --profile office-smoke --model-preset gpt-5-6-luna
nanobot benchmark run --profile office-release --model-preset gpt-5-6-luna
```

- `ci`：确定性 eval、cassette、代表性红队、报告重生和 adapter contract；无网络、无真实模型、不开 Langfuse。
- `office-smoke`：三套公开集的固定分层小集，完整记录 manifest、hard/Judge/audit。
- `office-release`：OCB 全量、固定 OfficeBench subset、PresentBench 手动 full。

输出必须区分：

```text
benchmarks/runtime/   deterministic/fake-provider
benchmarks/office/    true-model public benchmark
benchmarks/runs/      per-run manifest
```

run manifest 固定记录 benchmark revision、git SHA/dirty、Skill id/digest、模型、OfficeCLI version/SHA、Judge/evaluator、Token、成本、延迟、tool success、Agent steps、artifact hash 和 trace id。

## Office Skill 比较应怎样讲

P1.1 完成后，每次只启用一个被测 Skill，使用相同输入 snapshot、Luna、Policy、约束和 evaluator，输出两张表：

- capability coverage：`supported/unsupported/passed/failed`。
- common-task quality：hard gate、Judge、人审、Token、LLM/tool latency、tool success、Agent steps。

OfficePython 是公平 Python baseline，不能为了体现 OfficeCLI 优势而人为阉割。OfficeCLI 的统一跨格式命令、DOM/query/batch/view/validate/raw、复杂文件覆盖和较少循环必须由真实数据证明。

## README 与 Demo

README 必须明确：

- nanobot 原有与 Mybot 二开边界和 diff 口径；
- 无 Key cassette/CI 路径及真模型 benchmark profile；
- `office-automation` 当前状态与 `OfficePython` 迁移计划；
- Langfuse 使用日本区 Cloud、Mybot 本地报告不依赖它，并给出注册、项目 Key、`LANGFUSE_BASE_URL` 和历史同步步骤；
- official-comparable、compatible-custom-judge、Mybot adapter 的区别。

固定 demo：

```text
Skill 开关与同题对比
-> plan-only/自动执行
-> verified facts + Office artifacts
-> approval timeout + file_conflict
-> input lineage + kill/resume
-> parent/child trace + deterministic eval
-> OCB/OfficeBench/PresentBench smoke
-> 本地报告；配置日本区 Langfuse 时跳转 Experiment/Trace
```

安全和恢复演示使用 cassette/fixture 兜底，真模型只承担 Office 效果展示。完整版本和 3 分钟摘要各演练至少三遍。

## 当前禁止的表述

- “Langfuse Cloud 已接入”或“可观测已建立”：目前只确定日本区部署方案，没有 SDK sink 和 Cloud smoke 证据。
- “Langfuse 已自托管”：项目已选择 Cloud，仓库不提供本地部署栈。
- “OfficePython 已是通用 Skill”：当前仍是 `office-automation` 窄工作流。
- “OfficeBench 官方分数”：Mybot 使用 adapter 和不同 action space。
- “5 cases 代表真实模型质量”：它们是确定性 fixture。
- “PresentBench custom Judge 可直接与官方榜单比较”：必须标记 compatible。
- “多个 benchmark 的平均值是 Office 总分”：不同任务和 evaluator 不可直接平均。

## 面试主线

> Mybot 先用 deterministic fixture、cassette、Trace 和 hard gate 解决含 LLM 系统不可重复的问题，再用 OCB、OfficeBench Office subset 和 PresentBench 测真实 Office 理解、创建编辑和视觉生成。被测模型与 Judge 分离，高风险与分歧进入人工审计。Mybot 本地 JSONL 和报告始终可用，日本区 Langfuse Cloud 只是可选的开发者观测与实验后端；OfficeCLI 与通用 Python baseline 在相同条件下比较，让覆盖、正确率、成本和步骤数说明差异，而不是靠宣传。
