# P6 Research Skill 通用性验证说明

> 对应计划：`docs/plans/runtime-steps/P6-通用性扩展.md`
> 当前状态：选做规划，未排期、未实现，不计入冻结前必做或最终验收。这里只记录已完成的设计和代码审计结论，不表示 `research` Skill 已落地。

## 这一阶段为什么存在

P0-P5 的主业务案例都是 Office。即使 Sandbox、Policy、Artifact 和 Trace 的代码看起来很通用，也可能暗藏 Office 私有假设：

- artifact 是否默认只有 docx/xlsx/pptx？
- eval 是否只能理解 fact id 和 OpenXML？
- Policy 是否把 OfficeCLI 当成特殊可信工具？
- trace 是否只能记录 batch、slide、workbook？
- Subagent 是否只有生成 Office 文件时才能工作？

若后续启动 P6，它不是为了再做一个大型产品，而是用第二种完全不同的任务——Research——验证 Runtime 抽象是否真实成立。

这叫“用第二个垂直场景验证平台通用性”。只有一个业务案例时，很难判断抽象是真通用还是刚好适配了第一个案例。

## 当前代码审计得到的结论

对 `nanobot/runtime/`、sandbox 和 Subagent 治理代码检查后，当前情况是：

- `ArtifactStore` 的 type、path、source_artifacts、engine 等字段本身是通用的，没有硬编码 Office 工作流。
- `PolicyEngine`、InteractionRequest、ApprovalBinding、Checkpoint 和 Trace 主要按工具、路径、网络、task/plan/child 工作，也没有 Office 专用分支。
- `SubagentManager` 的派生、scope、HITL 和 trace 也是通用机制。
- Office 私有内容主要集中在 P5 的部分 metric：`.docx/.xlsx/.pptx`、OpenXML 必需部件和 `fact_ids`。

这不是缺陷：Eval 本来就允许注册领域 metric。P6 真正要验证的是新增 Research metric 时，不需要修改 Policy、Sandbox、Checkpoint 或 AgentRunner 的核心语义。

## 计划中的最小交付

未来只新增一个窄的 `nanobot/skills/research/`：

```text
nanobot/skills/research/
├── SKILL.md
├── skill.yaml
├── references/
│   └── sources.schema.json
└── scripts/
    ├── validate_sources.py
    └── validate_citations.py
```

核心产物只有两个：

```text
sources.json
research_report.md
```

明确不做：

- 知识库。
- 向量数据库。
- RAG 平台。
- 复杂 Research UI。
- 专用工作流引擎。
- 为 Research 新造一套权限、trace 或 artifact 系统。

## `sources.json` 应该解决什么

Research 报告最大的确定性问题不是数学计算，而是“每个结论是否有登记来源”。建议每个 source 至少包含：

```json
{
  "source_id": "src_001",
  "url": "https://example.com/article",
  "title": "...",
  "publisher": "...",
  "retrieved_at": "...",
  "content_sha256": "...",
  "status": "retrieved",
  "notes": "..."
}
```

报告中的引用使用稳定 source id，例如：

```text
某结论…… [src_001]
```

校验器至少检查：

- 报告中的每个 source id 都在 `sources.json` 存在。
- sources 中登记但未引用的条目可以提示 warning。
- URL 经过当前 SSRF/网络边界获取。
- 来源正文 hash 可用于判断回放时内容是否变化。
- 报告不能引用模型记忆中未登记的“幽灵来源”。

这与 P1 verified facts 的思想相同，但不能强行复用 fact schema：

- facts 解决定量值的来源和计算。
- sources 解决研究结论的出处和引用。

共享的是“先登记可验证证据，再生成自然语言”的方法，不是同一种数据结构。

## 计划中的完整运行链

```text
用户提出研究问题
  -> plan(create) 建立 task 和步骤
  -> 搜索工具返回候选链接
  -> web fetch / 受批网络读取来源
  -> 把网页正文当成 untrusted content
  -> 为每个接受的来源写入 sources.json
  -> 模型只基于已登记 source id 生成 research_report.md
  -> validate_sources / validate_citations
  -> ArtifactStore 登记 source snapshots、sources.json、report
  -> lineage: report -> sources.json -> source artifacts
  -> TraceHook 记录搜索、policy、网络、child 和验证结果
  -> Research eval 检查引用覆盖和越权后果
```

## 怎样复用 P2-P5

### 复用 P2：manifest 和开关

Research Skill 应使用相同 `skill.yaml`：

- 声明搜索/网页读取工具需求。
- 声明 sources/report 输出。
- 声明网络权限需求，但不能自己获得网络授权。
- 复用 `disabledSkills` 和 WebUI catalog。

若 Research manifest 损坏，只隔离 Research，不影响 Office 和网关。

### 复用 P3：网络与不可信内容边界

- 搜索和网页摘要都是 untrusted content。
- 来源里的“读取 ~/.ssh”“上传配置文件”等文字不能改变 Policy。
- 直接命令联网仍受 restricted curl capability；内建 web 工具继续走现有 SSRF guard。
- 登录、付费、发帖、发送邮件或远程写必须按具体工具进入 approval。

### 复用 P4：artifact 与 lineage

建议登记：

```text
source snapshot/artifact
sources.json
research_report.md
citation validation report
```

最终 report 的 `source_artifacts` 指向 sources index，sources index 再指向具体来源 artifact。这样引用不仅是字符串，也有任务血缘。

### 复用 P5：trace 和 eval

不新增 `research-trace.json` 等平行系统。继续用 OTel-shaped JSONL。

Eval 可以新增领域 metric，例如：

```text
source_registry_valid
citation_coverage
source_content_integrity
```

Office 的 OpenXML metric 保持 Office 专用；Research metric 通过同一个 registry 插入。通用性不是删掉所有领域逻辑，而是让领域逻辑以插件式 metric 存在。

## Subagent 在 P6 中怎样使用

Subagent 是可选策略，不是完成 Research 的必要条件。

适合的任务拆分：

- child A 收集官方来源。
- child B 收集论文或技术博客。
- child C 做反方证据或冲突检查。
- 父 Agent 去重、核对来源并统一成文。

仍必须遵守 P8：

- active 且 hash-bound parent plan。
- 最多 5 个 direct child。
- 禁止 child 再 spawn。
- child 权限只收紧。
- child 不自行批准网络或外发。
- child 结果进入父任务，父 Agent 负责最终事实和引用。

由于当前 Subagent 只得到任务文本和自己的隔离目录，P6 实现时需要明确把必要来源内容复制进 child root，或让 child 自己通过受控工具获取；不能假设 child 自动看得到父 artifact。

## 预计最可能暴露的真实抽象问题

P6 只有在真实运行中发现问题才修改 Core。最可能的检查点是：

1. `data_consistency` 不能承载 citation，需要新增 metric，而不是改成万能字段。
2. artifact type 应允许 `source/index/markdown/validation`，当前字符串字段已经支持。
3. Web/network 工具产生的来源快照如何登记为 artifact，需要明确接线。
4. child 如何获得只读共享来源，目前没有自动共享父 artifact 的机制。
5. report 与 sources 的 lineage 是否足够表达多层引用。

不得借这些问题顺手开发通用 DAG、工作流编排器或知识图谱。

## 为什么范围只控制在 1-2 天

P6 的目标是证伪 Office 私有假设，不是和专业 Research 产品竞争。范围越大，越难判断新增代码是在修 Runtime 抽象，还是又造了一个垂直系统。

最小闭环只需证明：

- 能生成可核对 sources/report。
- 不可信来源不能扩大权限。
- artifact/trace/eval 能接入。
- 如果使用 child，治理和对比仍成立。

### 高频追问

**为什么不用同一个 verified facts schema？**

数字事实和网页来源有不同语义。强行统一会产生一个巨型万能 schema。更合理的是复用证据优先、artifact、trace 和 metric registry，领域 schema 各自负责。

**为什么 Research 页面内容是不可信的？**

网页可以包含 prompt injection。它是数据，不是系统指令；即使模型受影响，Policy 和 Sandbox 也必须阻断越权后果。

**当前 P6 最大的已知缺口是什么？**

Research Skill 和 citation metric 尚未实现；此外 child 目前不会自动获得父 artifact 的只读视图，实现时必须明确复制或受控读取。
