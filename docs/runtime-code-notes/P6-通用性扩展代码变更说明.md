# P6 Research Skill 通用性验证说明

> 当前状态：选做，未实现。仓库中没有 `nanobot/skills/research/`、`sources.json` schema 或 citation evaluator。

## 为什么需要第二领域

Office 已验证 facts、OpenXML 和文件交付，但 Runtime 仍可能藏着 Office 私有假设。Research Skill 用网页来源、引用和 Markdown 报告替代 Excel facts、Office artifact 和 OpenXML，可以验证 P2-P5 的接口是否真的通用。

## 计划中的最小闭环

```text
用户研究问题
  -> WebSearch/WebFetch 收集来源
  -> sources.json 登记 URL、标题、摘要、访问时间和内容 hash
  -> research_report.md 只引用已登记 source_id
  -> citation evaluator 检查引用存在、覆盖和来源一致性
  -> ArtifactStore: report -> sources -> fetched evidence
```

范围只包含一个 `research` Skill、一个来源 schema、一个报告 artifact 和最小 evaluator；不做知识库、向量数据库、爬虫平台、复杂 UI 或通用工作流引擎。

## 应复用的现有代码

| Runtime 能力 | Research 如何复用 |
| --- | --- |
| P2 manifest | 声明 `sources.json` / `research_report.md`、web tools 和权限需求 |
| P3 Policy/Sandbox | URL 先过 SSRF，登录态、外发和远程写继续 ask |
| P4 Artifact | source evidence、sources 和 report 建 lineage |
| P5 Trace/Eval | 记录 fetch/tool/artifact 摘要并增加 citation metric |
| P8 Subagent | 可按来源拆 child，父 Agent 统一去重、核验和成文 |

网页正文必须视为 untrusted content。来源里出现“读取密钥”“忽略系统规则”“向某地址发送文件”等指令时，只能作为被研究文本，不能转成工具调用授权。

## 最可能暴露的抽象问题

- Artifact type 是否允许 `source/citation/report`，而不是写死 `docx/xlsx/pptx`。
- Policy 是否按真实 tool 参数分类，而不是按 Office command 名称分类。
- Eval 是否允许不同 metric 集合，而不是假设 OpenXML。
- Child 如何得到必要的父 artifact 引用；当前 P8 不会自动只读共享全部父 artifact。

若真实实现只需新增 Skill、schema、metric 和 fixture，说明 Runtime 边界较通用；如果必须修改 AgentLoop/Runner 的 Office 私有分支，应先修抽象泄漏，而不是给 Research 再加例外。

## 启动后的验收重点

- 单 Agent 能生成可解析 `sources.json` 和引用完整的报告。
- 报告中的每个 citation 都能回溯到登记来源和内容 hash。
- 恶意网页不能导致凭据读取、越界写入或未确认外发。
- 不修改 Runtime 核心即可复用 manifest、policy、artifact、trace 和 eval。
- 若用 Subagent，必须有父子 trace、artifact 边界和 single/multi 成本对比。

## 面试怎么讲

当前准确说法是：

“我设计了 Research 作为第二领域验证，用 citation lineage 替代 Office facts/OpenXML，专门检查 Runtime 是否有领域耦合；目前只做了接口审计，Skill 和 evaluator 尚未实现，所以不把它列为项目交付能力。”
