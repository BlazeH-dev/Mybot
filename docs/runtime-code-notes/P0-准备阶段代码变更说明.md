# P0 准备阶段代码变更说明

> 对应计划：`docs/plans/runtime-steps/P0-准备.md`
> 当前状态：已完成；当前 fixture 基线是中立 OfficeCLI 样本。

## 1. P0 为什么先做 fixture 和 CI

LLM 输出有随机性。如果输入、期望和执行环境也不断变化，就无法区分能力变化、偶然输出和代码
回归。P0 先固定三类证据：

1. 可重生、可人工查看的 Office 输入/输出样本。
2. 无 API key、无网络也能执行的 deterministic hard gate。
3. 每次 push 自动运行并重生报告的 CI 入口。

P0 不评判真模型文案质量；它回答的是“结构化接口、文件和 Runtime 硬门有没有被改坏”。

## 2. 当前中立 fixture

早期业务周报 fixture 已删除，当前基线位于：

```text
tests/fixtures/runtime_eval/
  office_baseline.json
  office_baseline.xlsx
```

JSON 与 XLSX 只验证 Runtime artifact、OpenXML 和事实一致性 hard gate，不绑定某个实现 Skill。

### 为什么从周报 fixture 改成中立 fixture

旧 fixture 同时绑定销售数据、会议纪要、固定 report/slide DSL、页数约束和周报措辞。它适合早期
垂直切片，却会让通用 OfficeCLI 的接口设计和后续公平 benchmark 继续围绕一个业务模板。

中立 fixture 只保留：

- DOCX paragraph/style/list/table/header/footer。
- XLSX sheet/cell/formula/basic chart。
- PPTX slide/title/content/basic layout。

公开 benchmark 的真实任务、gold 和 rubric 由 P5.1 固定 revision 后准备，不再借本地周报样本
冒充公开质量基线。

## 3. 确定性真值怎样保留

`sample.xlsx` 的 Data sheet 固定为：

```text
Item   Amount
Alpha  10
Beta   20
```

shared facts 回归用 `sum(Amount)` 得到 `total_amount=30`。P5 Core 的
`tests/fixtures/runtime_eval/office_baseline.json` 同时检查：

- artifact completion
- file openable
- data consistency 与 fact id
- OpenXML ZIP/XML/relationship
- visual sanity evidence
- replayability evidence

因此 fixture 收敛没有删除硬门，只删除了与通用接口无关的周报业务断言。

## 4. CI 回归门

`.github/workflows/ci.yml` 当前安装 Python 3.11、项目 dev 依赖和 Linux Bubblewrap，然后执行：

```text
ruff check nanobot/ tests/runtime/
pytest tests/runtime/
       tests/skills/test_officecli_runtime.py
       Plan / model / settings deterministic tests
```

随后重生：

- `benchmarks/latest.json` / `latest.md`
- `benchmarks/subagent-comparison.json` / `.md`

CI 用 `cmp` 做字节级比较。fixture path、digest 或 metric 输出变化而未更新基线时，CI 会失败。

## 5. 为什么不把全量上游测试都作为 P0 门

上游套件包含网络、API key、本地端口和用户目录依赖。把这些环境失败混进二开硬门会掩盖真正
回归。当前策略是：

- CI 固定运行 Mybot deterministic core。
- 阶段实现按 blast radius 增加定向测试。
- 本地仍可跑全量 `pytest tests/ -q`，但不把无凭据的环境失败伪装成产品回归。

## 6. 验证

```bash
source venv/bin/activate
pytest tests/skills/test_officecli_runtime.py tests/runtime/test_replay_trace_eval.py -q
python -m nanobot.runtime.evals.report \
  tests/fixtures/runtime_eval/*.json \
  --json /tmp/runtime-eval.json \
  --markdown /tmp/runtime-eval.md
cmp /tmp/runtime-eval.json benchmarks/latest.json
cmp /tmp/runtime-eval.md benchmarks/latest.md
```

## 7. 已知边界

- 中立 fixture 只证明接口与文件结构，不是 OCB 真模型质量分。
- CI 不依赖真实 LibreOffice；真实渲染版本由 P5.1 smoke/release prepare 锁定。
- `benchmarks/latest.*` 是 P5 Core deterministic 报告，不是 Langfuse 真模型 Dataset Run。

## 面试怎么讲

> 我先把 Office 输入做成可重生的中立 OpenXML fixture，再让 CI 对 Runtime hard gate 和已提交
> 报告做确定性重生。这样真模型 benchmark 波动不会污染代码正确性判断；后续 Langfuse 实验负责
> 质量、成本和人工审核，本地 fixture 负责接口、文件与安全回归。
