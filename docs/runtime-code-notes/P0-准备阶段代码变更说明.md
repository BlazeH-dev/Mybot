> 对应计划：`docs/plans/runtime-steps/P0-准备.md`
> 执行状态：已完成固定 Office fixture 与 CI smoke 回归门。
> 2026-07-16：阶段计划仅压缩重复说明，已落地代码、测试和验收边界不变。

## 阶段目标

P0 的目标不是增加 Agent 能力，而是先给后续 P1-P8 建一个稳定的“地基”：

- 一份可重复生成、可人工复核、可被脚本读取的 Office 周报输入。
- 一组固定期望值和任务约束，用来判断后续脚本、skill、eval 是否真的正确。
- 一条从第一天就存在的 CI 回归门，让每次改动都能自动跑确定性 smoke 测试。

换句话说，P0 解决的是“以后怎么证明我们没有把系统改坏”的问题。

如果把 Runtime 比作一座楼，P0 不是先盖房间，而是先统一尺子、承重标准和验收表。没有这一层，后面每次模型输出不同，都很难判断是能力提升、随机波动，还是代码回归。

## 先理解三个测试概念

### Fixture：固定输入

Fixture 是测试反复使用的输入资产。这里不是每次随机造一份 Excel，而是把 8 行销售数据、会议纪要和约束固定下来。这样不同 Skill、不同版本和不同模型面对的是同一道题。

### Golden truth：人工确认的正确答案

`expected_metrics.json` 是黄金真值。它不是模型生成的答案，而是人工可复核的 GMV、订单、访客、转化率、Top 区域等结果。系统输出必须向它对齐。

### Smoke gate：小而稳定的回归门

Smoke test 不追求覆盖整个上游项目，而是先覆盖 Mybot 二开最重要、最确定的链路。它的价值是每次 push 都能快速回答：“核心路径还活着吗？”

### Office golden fixture

tests/fixtures/office_weekly/

主要文件：

- `make_fixture.py`：用 `openpyxl` 生成固定 Excel 工作簿。

### CI smoke 回归门

新增 / 收敛：

```text
.github/workflows/ci.yml
```

CI 做六件事：

1. 使用 Python 3.11。
2. 安装项目、dev 依赖和 Linux Bubblewrap。

## 为什么这么做

### 1. 先固定输入，再谈 Agent 能力

Agent 项目很容易陷入“模型这次看起来答对了”的主观验收。P0 用固定 Excel、会议纪要、期望指标和约束，把后续验收变成机器可重复执行的检查：

- Excel 里有固定行数、固定字段和固定数值。
- `expected_metrics.json` 记录 GMV、订单量、访客数、转化率、客单价、Top 区域、Top 渠道等真值。
- `expected_constraints.json` 记录交付物和质量约束。

这样 P1 的脚本、P5 的 eval、P7 的 demo 都可以用同一份输入说话。

### 2. 降低后续测试噪声

fixture 数据故意设计得小而完整：

- 只有 8 行销售数据，便于人工复核。
- 数值大多是整数，减少浮点误差。
- 覆盖求和、比率、分组 Top 等常见办公指标。
- 会议纪要覆盖结论、风险、行动项，后续可评测文案覆盖度。

这让后续失败更容易定位：如果数字错了，基本就是脚本或 DSL 处理错了，不是数据集太复杂。

### 3. CI 先小后大，避免被旧环境依赖拖垮

本地全量 pytest 摸底还有大量旧测试依赖网络、API key、端口、home 目录等环境条件。P0 没有强行把全量测试塞进 CI，而是先建立一个确定性 smoke gate。

这个取舍的重点是：

- 先有一个稳定、公开、可持续增长的回归门。
- 后续 P1-P8 每完成一块，就把确定性测试纳入这个门。
- 不让和当前二开目标无关的旧环境失败阻塞开发节奏。

## 怎么做的

### fixture 生成路径

`make_fixture.py` 把表头和行数据写死在脚本中：

```text
date / region / channel / visitors / orders / gmv_cny
```

脚本用 `openpyxl.Workbook` 创建 `sales_data.xlsx`，并做了基础样式设置：

- 标题行加深色背景和白色粗体。
- 销售表设置为 Excel Table。
- 固定首行。
- 给 GMV 列设置千分位格式。

这样 `sales_data.xlsx` 不是手工二进制黑盒，而是可以通过脚本重新生成的测试资产。

### 指标真值设计

`expected_metrics.json` 记录两层值：

- `value`：机器比对用的原始值。
- `display_value`：最终报告 / PPT 中应该出现的人类可读值。

例如：

- `total_gmv_cny` 的 `value` 是 `1710000`，`display_value` 是 `CNY 1,710,000`。
- `conversion_rate` 的 `value` 是 `0.0780821918`，`display_value` 是 `7.81%`。

这个结构为 P1 的 `verified_facts.json` 打下了格式基础。

### fixture 自检

`test_fixture.py` 重新打开 `sales_data.xlsx`，直接从表格行里计算：

- GMV 合计。
- 订单量。
- 访客数。
- 转化率。

再与 `expected_metrics.json` 做断言。这样可以防止 Excel 文件、生成脚本和期望 JSON 三者漂移。

### CI smoke

`.github/workflows/ci.yml` 当前不跑全量测试，而是选择：

- P3/P4/P5/P8 Runtime Core 回归。
- P0 fixture 自检。
- P1 Office 确定性链与 Plan Tool/执行模式测试。
- 模型预设配置测试。
- `/model` 命令测试。
- WebUI settings API 测试。

这些测试覆盖了当前二开项目的关键稳定面：模型切换、配置保存、Office fixture 基线，以及 Runtime sandbox/policy/HITL/OCC/artifact/checkpoint/Subagent/trace/eval 硬门。

### 手算一次指标，理解为什么 fixture 容易排错

8 行数据相加得到：

```text
visitors = 1200 + 900 + 650 + 1100 + 700 + 950 + 800 + 1000 = 7300
orders   = 96 + 72 + 39 + 99 + 42 + 76 + 56 + 90 = 570
gmv      = 1,710,000
conversion_rate = 570 / 7300 = 0.078082... = 7.81%
```

这种数据规模让失败定位很直接：

- Excel 自己算不出 7300，说明 fixture 或读取逻辑错了。
- facts 算出 7.8 而不是 0.078，说明百分比单位处理错了。
- PPT 显示 0.078%，说明展示格式错了。
- 报告数字正确但没有 fact id，说明 grounding 链断了。

这就是“把复杂 Agent 问题拆成可确定性验证的小问题”。

### 2026-07-16 模型预设与 WebUI 管理更新

- 内置 LLM 预设由 DeepSeek + MiMo 调整为 DeepSeek + GPT-5.6 Sol/Terra/Luna；MiMo Provider 仅保留语音转写用途。
- 配置加载器退休未被用户修改的 MiMo 预设，并清理对应 active/fallback 引用；用户修改过的同名配置继续保留。
- Settings API 增加 `is_builtin` 和自定义模型配置删除接口；Default 与内置预设不可删除。
- WebUI 设置页改为模型配置列表，新增/编辑共用弹窗，自定义配置提供确认删除；输入框快速切换菜单可进入模型管理。
- 回归覆盖内置预设、迁移、自定义配置保护、删除限制、Settings 路由、前端列表与输入框入口。

### 2026-07-16 未配置 API Key 的网关启动

- `nanobot gateway` 在当前默认或已选的需 Key Provider 尚未配置时，不再在启动阶段退出；Provider 工厂生成不访问网络、不会请求模型或调用工具的占位 Provider，使 WebUI 设置页可正常打开。
- 占位 Provider 的聊天响应只提示用户进入“设置 → Providers”保存对应 API Key；保存后不要求重启，Agent 在下一条新消息开始前加载严格的最新 Provider 快照并自动切换为真实 Provider。
- 容错仅覆盖明确的“缺少 API Key”错误。无效 Provider、Azure 缺少必需 `api_base` 等非凭据配置错误仍保持 fail-fast，避免网关以损坏配置运行。
- 显式模型前缀（如 `openai-codex/...`、`github-copilot/...`、`ollama/...`）优先于遗留或默认 provider 字段，避免路由回落到 DeepSeek；桌面端旧 bootstrap 值即使与内置 presets 共存也会先从持久配置清除，再仅注入运行时副本。
- 回归覆盖 DeepSeek/OpenAI 的无 Key 启动、占位响应无工具调用、严格 Provider 工厂仍拒绝无 Key、非凭据错误不被掩盖，以及 Settings API 保存 Key 后的运行时热切换和密钥脱敏。

### 2026-07-16 首次 Provider 配置引导与模型弹窗布局

- WebUI 在没有任何已配置且可聊天的 Provider 时，不再展示内置模型预设、模型编辑或“新增配置”入口；页面优先呈现 Provider 配置引导和现有 Provider 列表，避免用户进入无可选 Provider 的无效模型表单。
- 用户保存 Provider 凭据后，模型配置区自动恢复；无需额外的首次初始化步骤，沿用已有默认模型和模型配置管理流程。
- 模型配置弹窗将“模型 + Provider”改为响应式等宽双列，并让两个选择器填满列宽，消除 `360px + 210px` 固定控件宽度超过弹窗内容区造成的视觉溢出。
- 前端回归覆盖无 Provider 的引导状态、隐藏模型配置入口，以及可用 Provider 下的弹窗选择器宽度契约。

### 2026-07-16 配置 Provider 后的模型收敛

- 保存 Provider 凭据后，若当前默认模型的 Provider 仍不可用，Settings API 自动选择该 Provider 的第一个已保存预设；例如保存 OpenAI 中转凭据后自动启用 `gpt-5-6-sol`，不继续保留不可用的 DeepSeek 默认模型。
- 模型配置列表只渲染已配置且支持聊天的 Provider 对应预设。未配置的 DeepSeek、OpenAI 或自定义 Provider 模型不会与当前可用模型混排；Provider 配置列表仍完整保留，方便随后补充凭据。
- 回归覆盖 OpenAI 首次配置后的默认预设切换，以及只显示已配置 Provider 模型的前端过滤。

### 30 秒回答

> P0 我没有急着接更多模型或做复杂 Agent，而是先建立固定 Office fixture、人工真值和 CI smoke gate。因为 LLM 输出有随机性，如果输入和期望都不固定，后面很难区分真实能力提升和偶然结果。P1 的 facts、P5 的 eval、P7 的 demo 都复用同一套基线。

### 常见追问

**为什么不直接跑全量 pytest？**

上游全量测试里有网络、API Key、端口和用户目录依赖，把这些不稳定环境问题直接作为二开 CI 硬门，会造成大量与本次变更无关的噪声。当前策略是先圈定确定性核心，再逐步扩大范围，同时保留全量摸底结果。

**为什么 Excel 二进制文件还要保留生成脚本？**

因为二进制文件本身难 review。生成脚本让数据来源、表头、样式和行内容都能在 Git diff 中检查，也可以在文件损坏时重建。

**为什么既有 `value` 又有 `display_value`？**

`value` 用于计算和精确比较，`display_value` 用于 DOCX/PPTX 展示。把计算值和展示格式分开，可以避免货币千分位、百分比和整数格式污染底层计算。
