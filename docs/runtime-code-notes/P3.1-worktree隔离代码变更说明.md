# P3.1 WebUI Workspace / Git Worktree 隔离说明

> 当前状态：选做，未实现。仓库中没有 `WorktreeManager`、worktree registry、per-chat 分支创建或 WebUI 隔离模式代码。

## 这一阶段想解决什么

P3 的 `WorkspaceScope` 和 OS sandbox 解决“进程能访问哪里”，但多个聊天同时修改同一个 Git checkout 时，仍可能互相看到未提交文件、分支切换和构建产物。P3.1 计划用每聊天独立 worktree 解决 Git 工作目录冲突。

它不是安全沙箱：Full Access 下进程仍可能访问原仓库；Default Permission 仍必须依靠 P3 Seatbelt/Bubblewrap。

## 已确认的契约

```text
新聊天选择 direct | worktree
  -> 服务端检查 repo root / HEAD / dirty
  -> 用户确认“从 HEAD 创建”，不复制 dirty diff
  -> 创建 mybot/chat-<chat_id> + 独立 worktree
  -> session 持久化 server-side binding
  -> tool / preview / artifact 使用 effective worktree path
  -> 删除聊天时仅清理 clean && HEAD == base_commit 的 worktree
```

- 默认仍是 `direct`，旧 session 和非 Git 目录不受影响。
- tracked/untracked 变化不会被静默复制；创建前必须明确提示。
- worktree chat fork 只允许源 worktree clean，从源 `HEAD` 创建新分支。
- dirty 或存在新 commit 的 worktree一律保留，不使用 force remove。
- 客户端只能提交选择，不能伪造 common dir、branch、worktree root 或 sandbox roots。
- 首版不自动 commit、merge、push、rebase，不向 Agent 开放 Git common dir 写权限。

## 如果启动，代码应放在哪里

| 模块 | 责任 |
| --- | --- |
| `nanobot/workspaces/worktrees.py` | inspect/create/resolve/fork/cleanup/list，固定 Git argv |
| `~/.nanobot/worktrees/registry.json` | chat、repo、branch、base commit、path、status 的服务端绑定 |
| Session metadata | 只保存 binding id，不信任客户端重传绝对路径 |
| WebSocket/HTTP | 创建、fork、删除和只读列表控制面 |
| WebUI | Direct/Worktree 选择、HEAD 确认、保留/清理状态 |

registry 的 read-modify-write 需要跨进程锁和原子替换；`creating/removing` 中间状态需要启动对账。Git 命令由宿主控制面生成精确 argv，不能接收模型提供的 branch/path/flags。

## 为什么现在不实现

Runtime Core 已有 workspace scope、sandbox、OCC 和 child artifact root。Worktree 主要改善多聊天编码体验，却引入 Git 版本、dirty 状态、子目录映射、fork、清理和崩溃恢复等长期维护成本。没有真实冲突数据前，它不应阻塞 P5/P7 的可观测和交付闭环。

## 启动后的验收重点

- Direct 模式和旧 session 完全兼容。
- repo 子目录映射、HEAD 变化、branch/path 碰撞结构化失败。
- dirty fork 拒绝且不留下 registry/path；clean fork 正确创建新分支。
- clean 且无新 commit 才自动清理，dirty/committed worktree 保留率 100%。
- 并发 create/fork/cleanup 不覆盖 registry；进程中断后能对账。
- binding 丢失时 fail closed，不能静默回退原仓库。
- worktree 不改变 P3 sandbox 的安全结论。

## 面试怎么讲

当前只能说：

“我把项目根、OS sandbox 和 Git worktree 分成三层。前两层已经实现，worktree 是未排期的产品增强；我完成了 HEAD 基线、dirty 不复制、保守清理和服务端 binding 的契约设计，但没有把它写成现有能力。”

不能说“系统已经支持每聊天 worktree”或“worktree 能防止恶意进程越权”。
