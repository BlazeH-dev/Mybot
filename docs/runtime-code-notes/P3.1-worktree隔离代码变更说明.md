# P3.1 WebUI Workspace / Git Worktree 隔离说明

> 对应计划：`docs/plans/runtime-steps/P3.1-worktree隔离.md`
> 当前状态：选做规划，未排期、未实现。只有冻结前必做完成、真实多聊天 Git 冲突证明收益且用户明确提高优先级后才启动；本文不能作为现有代码能力、Runtime Core 验收或测试证据。

## 这一阶段为什么存在

当前 Mybot 已按聊天持久化 `WorkspaceScope`，但多个聊天指向同一个 Git 项目时，仍会共享同一工作树：

- 一个聊天修改的文件会立即影响另一个聊天。
- 不同任务难以独立保留分支和 commit 历史。
- 聊天 fork 只能复制会话，不会复制可写工作目录。
- 用户当前 checkout 中的未提交修改容易与 Agent 任务混在一起。

P3.1 若后续启动，计划使用 Git 原生 worktree，为用户显式选择的 WebUI 聊天创建独立工作树和分支。它解决的是任务之间的文件与 Git 状态隔离，不是恶意进程隔离。

## 与 P3 Sandbox 的边界

必须区分三件事：

```text
WorkspaceScope
  -> 决定当前聊天的项目根和 restricted/full access profile

Git worktree
  -> 为聊天提供独立工作树、branch 和 HEAD

OS Sandbox
  -> 用 Seatbelt/Bubblewrap 强制限制进程实际可访问的系统资源
```

Worktree 不是安全边界。Default Permission 下，worktree 的 effective path 仍必须交给已完成的 P3 Sandbox；Full Access 下，Agent 仍可能访问原仓库或其他本地路径。P3.1 不能替代 P3 的统一 Exec launcher、受批网络闭环或 OS 强制边界。

## 已确认的产品契约

### 新聊天显式选择

- 只在 localhost WebUI 新聊天中提供 `Direct | Worktree`，默认 `Direct`。
- 旧会话、非 Git 目录、CLI、其他 channel 继续使用 direct workspace。
- Worktree 聊天创建后不能切换项目或 isolation mode；仅允许在任务未运行时切换 Default Permission / Full Access。
- 如果用户选择仓库子目录，聊天仍以该子目录为项目根，但 effective path 映射到新 worktree 中的同一相对位置。

### 从 HEAD 创建，不复制 dirty 状态

源仓存在 tracked 或 untracked 变化时，服务端必须告诉用户新 worktree 只基于当前 `HEAD`，不会包含未提交变化；用户二次确认后才创建。

ignored 文件不参与 dirty 阻断，也不会被复制。首版不尝试自动 stash、生成 patch、复制文件或猜测哪些未提交内容属于当前任务。

### 聊天 fork

- Direct 聊天仍 fork 为 Direct。
- Worktree 聊天只有源工作树 clean 时才能 fork。
- 新 worktree 从源聊天当前 `HEAD` 创建，因此已提交工作可以继承，未提交 diff 不会被隐式复制。
- fork 任一步骤失败都要回滚尚无用户工作的临时 worktree、branch 和 registry 记录。

### 保守清理

自动清理只允许删除可证明没有新工作的 worktree：

```text
clean && HEAD == base_commit
```

只要存在 tracked/untracked 修改或 `HEAD != base_commit`，就保留 worktree 和分支。是否已经 push、merge 或 cherry-pick 不能作为自动删除依据，因为首版没有可靠的远端与目标分支证明链。

## 计划中的代码落点

计划新增：

```text
nanobot/workspaces/
└── worktrees.py
```

核心对象为宿主控制面的 `WorktreeManager`：

```text
inspect_source(path)
create(chat_id, source_path, expected_head)
resolve(binding)
fork(source_binding, new_chat_id)
cleanup(binding)
list_managed()
```

Git 操作必须使用固定 argv，由服务端生成 branch 和 worktree path，不接受模型或客户端提交任意 Git flags、common dir 或 filesystem root。耗时 Git 调用放入 worker thread，避免阻塞 WebSocket event loop。

## 持久化设计

计划使用：

```text
~/.nanobot/worktrees/<repo_id>/<chat_id>/
~/.nanobot/worktrees/registry.json
```

- `repo_id` 从 resolved Git common dir 计算稳定 SHA-256 摘要。
- branch 固定为 `mybot/chat-<chat_id>`。
- registry 原子替换并限制为 `0600`，记录 source repo、common dir、worktree root、相对子目录、branch、base commit 和状态。
- create/fork/cleanup 与 registry read-modify-write 使用跨进程 advisory lock；原子替换只能防止半写文件，不能单独防止两个进程读取旧版本后互相覆盖。
- 操作先写入 `creating|removing` 中间状态；进程中断后，启动对账根据 registry 与 `git worktree list --porcelain` 恢复可证明结果，否则进入 `attention_required`。
- session metadata 只保存服务端签发的 `workspace_binding`；客户端可提交的 `workspace_scope` 不能伪造 worktree root、common dir 或额外 sandbox roots。
- 启动恢复时对 registry 与 `git worktree list --porcelain` 做对账；缺失或冲突项标为 `attention_required`，不能静默回退原仓库。

## 为什么首版不增加 Agent Git 工具

Worktree 生命周期由宿主控制面管理，不等于 Agent Core 需要获得 Git 元数据写权限。首版明确不增加结构化 `git add/commit/push/merge`，也不为普通 Shell 开放 Git common dir 写权限。

这样可以先验证聊天级目录隔离，而不同时引入凭据、远端写、分支发布、rebase/merge 冲突和不可逆历史修改。后续只有在真实编码任务证明需求稳定后，才把 Git 写操作作为独立 Skill 或结构化工具设计，并继续经过 P3 Policy/approval。

## 测试计划

实现时至少需要以下证据：

- Direct 默认与旧 session schema 保持兼容。
- Git repo 和子目录可以创建正确 worktree；非 Git、bare repo、branch/path 碰撞、`HEAD` 变化都结构化失败。
- 源仓 dirty 时必须二次确认，且新 worktree 不包含 tracked/untracked/ignored 未提交内容。
- 工具 cwd、文件边界、artifact path、重启恢复和 WebUI 展示都使用同一个 effective path。
- clean fork 成功；dirty fork 拒绝且不留下 worktree、branch 或 registry 残留。
- 只有 `clean && HEAD == base_commit` 会自动清理；dirty 或有新 commit 的保留率为 100%。
- 并发 create/fork/cleanup 不会丢 registry 条目、复用 branch/path 或误删其他聊天 worktree；`creating|removing` 中断状态可对账。
- 伪造客户端 binding、common dir 或 root 不能扩大 `WorkspaceScope` 和 sandbox roots。
- Default Permission 的 worktree 进程仍通过 P3 Seatbelt/Bubblewrap 验证，不能把 worktree 测试替代 sandbox 测试。

## 当前不能声称的能力

- WebUI 目前还没有 Direct/Worktree 选择器。
- 还没有 `WorktreeManager`、registry、聊天绑定、fork 或安全清理实现。
- 不支持自动 commit、merge、push、rebase、submodule 或 Git LFS 初始化。
- 不为 Subagent 创建嵌套 worktree；P8 child 仍使用 task-scoped artifact root。
- Worktree 不是容器、虚拟机或 OS sandbox。

## 面试怎么讲

### 当前可以说什么

> 我把 workspace 安全范围、OS sandbox 和 Git worktree 分成三层。P3.1 已完成契约设计：WebUI 聊天可选独立 worktree，从明确 HEAD 创建，dirty 状态不自动复制，只有 clean 且没有新 commit 才自动清理。但这部分尚未实现，不能当成当前产品能力。

### 完成后可以怎样讲

> 我没有把 worktree 当安全沙箱，而是用它隔离并行聊天的文件和分支状态。安全仍由 WorkspaceScope 与 Seatbelt/Bubblewrap 负责；worktree 控制面只使用固定 Git argv，并以保守清理保证 dirty 修改和新 commit 不会被自动删除。
