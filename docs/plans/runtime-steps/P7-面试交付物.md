# P7 交付物、可观测与面试证明

> 状态：持续维护，公开 benchmark、Langfuse sink、OfficePython 通用化和一键入口尚未完成。
> 目标：让陌生人 10 分钟内理解项目、复现核心证据，并明确区分确定性、fake-provider、真模型和人工审计结果。

## 1. 一键评测入口

统一 CLI：

```bash
nanobot benchmark run --profile ci
nanobot benchmark run --profile office-smoke --model-preset gpt-5-6-luna
nanobot benchmark run --profile office-release --model-preset gpt-5-6-luna
```

- `ci`：P5 确定性 eval、cassette、代表性红队、报告重生和 benchmark adapter contract；无 API key、无网络、不开 Langfuse。
- `office-smoke`：OCB、OfficeBench-Office/Mybot adapter、PresentBench 固定分层子集；被测 Agent 固定 `gpt-5-6-luna`，日常 Judge 固定 `gpt-5-6-sol`。
- `office-release`：OCB 公开全量、固定 OfficeBench Office subset、PresentBench 手动 full。严格复现上游 evaluator/Judge 才标记 `official-comparable`，否则标记 `compatible-custom-judge`。

每个 run manifest 必须记录 benchmark/revision/case、git SHA/dirty、Skill id/digest、模型 preset、OfficeCLI 版本和 binary SHA、Judge/prompt/evaluator 版本、Token、成本、P50/P95、tool success/latency、Agent steps、artifact hash 和 trace id。

## 2. 结果分层与指标

评估固定为：

1. 确定性 hard gate：数字、文件、OpenXML、artifact、Policy、OCC、HITL、恢复和安全后果。
2. LLM semantic Judge：内容覆盖、OfficeBench 开放语义、PresentBench 内容/视觉 rubric。
3. 人工 audit：全量审计高风险和 hard/Judge 冲突；首次基线和发布版本抽样约 5%。

不采集对话量、用户满意度、CPU、内存或 GPU。公开技术指标只包含任务/benchmark 成功、LLM/tool 成功率与错误、P50/P95、Token/成本、Agent steps、等待/恢复和评估分数。任何 hard failure 都不能被软分平均。

报告位置：

```text
benchmarks/latest.md                 总索引与结果类型说明
benchmarks/runtime/latest.{json,md} 确定性/fake-provider 证据
benchmarks/office/latest.{json,md}  真模型公开 benchmark
benchmarks/runs/<run-id>/manifest.json
docs/plans/metrics-baseline.md       可比 run 的历史趋势
```

原始 benchmark 数据、完整 trace 和大体积 Office 产物默认不提交仓库。

## 3. Office Skill 对比证据

P1.1 完成后，对比 `officecli` 与 `office-python`：

- capability coverage 表：`supported/unsupported/passed/failed`；
- common-task quality 表：相同输入、Luna、Policy、约束和 evaluator 下的 hard/Judge/audit、Token、LLM/tool latency、tool success 和 Agent steps；
- OCB 主要证明文件理解，OfficeBench Office subset 证明 Word/Excel 创建编辑，PresentBench 证明 PPT 创建和视觉质量；
- 不把三个 benchmark 合成一个模糊总分，也不把 `unsupported` 伪装成执行失败。

OfficePython 是公平的 Python Office baseline，不以人为限制衬托 OfficeCLI。OfficeCLI 的优势必须来自更高覆盖、复杂文件保真、统一命令/DOM/query/batch/view/validate/raw、较少循环或更稳定结果。

## 4. Langfuse 与 Mybot WebUI

Langfuse 部署固定采用日本区 Langfuse Cloud，注册地址和 SDK `baseUrl` 都是 `https://jp.cloud.langfuse.com`。仓库不提供自托管 Compose，也不把本地 Langfuse 基础设施作为交付物。P7 要求：

- P5.1 使用可选 Python SDK sink；默认本地脱敏 JSONL，Langfuse 关闭时任务和报告正常。
- 支持 `nanobot observability sync` 在之后同步历史 run。
- Langfuse UI用于开发者查看 Trace、Datasets、Experiments、Scores 和失败 case，下钻比较 `officecli-luna` 与 `office-python-luna`。
- Mybot WebUI仍从 Runtime/task/report 展示实时步骤、等待、artifact、benchmark 进度和评估摘要；只有配置日本区项目 Key 并成功获得远程 id 时显示“查看完整 Trace”链接，链接从配置的 `baseUrl` 生成。
- API Key 在日本区项目的 Project Settings 创建，只保存在本机后端配置或环境变量中，不进入前端、仓库、报告和 trace。
- 各区域账号和数据隔离；不能使用默认欧盟入口后再假设可以原地切到日本区。需要换区时按独立账号和数据迁移处理。
- Cloud 模式不要求本机安装 Redis、MinIO、ClickHouse 或 PostgreSQL。
- 日本区属于跨境数据传输。普通私有任务默认只上传脱敏 metadata，不上传原始 Office 文件、完整正文、密钥和个人信息；真实公司或敏感数据在合规审查前保持远程 sink 关闭。
