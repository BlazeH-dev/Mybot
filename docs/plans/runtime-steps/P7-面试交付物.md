# P7 面试交付物 — 详细步骤

> 所属：`docs/plans/2026-06-16-agent-runtime增量开发计划.md` · 2026-07-03 新增阶段
> 状态：持续执行。2026-07-14 同步双 Office Skill、持久化审批、安全恢复与 Subagent 主线；demo 不再受 3 分钟硬限制，但保留 3 分钟摘要讲法。
> 阶段出口：陌生面试官 10 分钟内看懂项目价值、能照 README 复现 demo；每个亮点有量化数据和答辩话术。

主题：**把工程成果转成面试表达**。工程做得好但讲不出来 = 白做。本阶段产出三样东西：可复现的数据（benchmark）、可复现的演示（README + demo）、可复现的表达（答辩稿）。这一阶段成本低（约 2–4 天），但直接决定前面所有阶段在面试里的兑换率——**必做，且不要压缩到最后一周才开始**。

## S7.1 一键 benchmark + 指标基线报告

### 目标
一条命令跑全部评测并汇总成指标报告，形成随迭代变化的趋势表。

### 对应工程点
**评测即产品**。面试潜规则：能报出"从 X 到 Y"的候选人比只报"做了什么"的可信一个量级。基线必须自动化，否则不会被坚持记录。

### 改动点
- 新增一键入口（`scripts/run_benchmark.py` 或 make target）：
  - 跑全部确定性 eval（P5.2/5.3）+ 红队 case（P5.6；关键 smoke 走回放，完整集可手动跑）。
  - 可选参数触发多模型矩阵（P5.7，手动跑，不进 CI）。
  - 从 trace 汇总 token/成本/时长。
- **报告双写**（2026-07-06 调整，修复 README 引用矛盾——`docs/plans/` 在 `.gitignore` 里，公开仓库的 README 不能引用它）：
  - repo 内 `benchmarks/latest.md`（进 git，README 指标表引用它；demo GIF 等 README 资产同理放 repo 内）。
  - `docs/plans/metrics-baseline.md`（本地详尽历史，追加模式）：任务成功率、数字一致性、注入诱导越权副作用、未确认外发、文件冲突、每任务 token/成本、P95 时长、恢复成功率和 Subagent 开销。
- 回填历史：把 P1 起手动记录的指标整理进同一文档。

### 实施步骤
1. 汇总器：读 eval report + trace → 指标 dict。
2. Markdown 渲染（对齐方案 §2.3 的指标表结构）。
3. 每完成一个阶段跑一次，攒出 ≥3 个时间点的趋势。

### 验收
- 一条命令产出完整报告。
- 报告含至少两个时间点的对比（有"变化"可讲）。

### 依赖
P5（eval/trace/红队）；P4.7（恢复成功率一项，缺则标 N/A）。

## S7.2 README + 架构图 + 完整治理 demo 脚本

### 目标
项目的"门面"：不看代码也能明白这是什么、为什么难、怎么验证。

### 对应工程点
**可复现的演示**。面试官（和简历初筛）平均给一个项目的时间是分钟级；README 第一屏必须完成"定位 + 亮点 + 数据"三件事。

### 改动点
- **README**（建议中英各一份或中文为主）：
  - 第一屏：一句话定位（方案 §1 面试版）+ 亮点列表（每条带指标）+ demo GIF。
  - 分层架构图：`WebUI/WS channel → MessageBus → AgentLoop/Runner → Tool Registry（Policy 层包裹）→ Skills（渐进披露）`，旁路 `runtime/：policy / trace / artifacts / checkpoint / replay / evals`；图上明确标出"二开新增"与"nanobot 原有"的边界（面试官最关心你做了哪部分）。
  - **二开边界证据**（2026-07-06 新增）：对上游 v0.2.1 基线的 `git diff --stat` 统计表（runtime/ 包 + office skill + tests），与架构图分色互相印证。
  - Quickstart：从 clone 到跑通 demo 的最短路径；**提供轻量 cassette 的无 API key demo 路径**（面试官/初筛没有 key 也能复现关键路径）。
  - 指标表：直接引用 repo 内 `benchmarks/latest.md` 最新一节。
  - 设计取舍 FAQ：为什么两个 Office Skill 独立、为什么事实层共享但 DSL 不共享、为什么 ask 持久化后结束执行、为什么安全指标看后果而非万能注入检测。
  - OfficeCLI FAQ：默认优先 OfficeCLI、何时选择 Python Skill、完整 OfficeCLI 能力如何由 Runtime 分级治理、如何通过 `disabledSkills` 开关。
- **完整治理 demo 脚本**：
  1. 展示两个 Office Skill 与启用/禁用开关，默认选择 OfficeCLI。
  2. 上传 Excel + 会议纪要，保存输入 snapshot，静态 plan tool 返回 hash 并等待确认。
  3. 生成 docx/PPT，展示 verified facts 与不同 Skill 的独立中间产物。
  4. 触发高风险修改，Runtime 落 pending approval 后结束当前执行；批准后恢复。
  5. 演示读取后外部修改导致 `file_conflict`。
  6. 展示 artifact lineage 与输入 snapshot。
  7. kill 网关后从 completed/pending/uncertain checkpoint 安全恢复。
  8. 触发含子 Agent 的 Office/Research 任务，展示最多 5 个直接 child 的父子 trace、隔离产物和预算。
  9. 查看硬门 eval 与单 Agent/子 Agent 成本时长对比。
- 录制 demo GIF/短视频，README 内嵌。

### 实施步骤
1. 先写 demo 脚本并真跑三遍（措辞、时长、失败兜底都要演练）。
2. 画架构图（draw.io/excalidraw，导出 SVG 入库）。
3. 写 README，找一个没接触过项目的人试读 10 分钟给反馈。

### 验收
- 陌生人按 README 能从零跑通 demo。
- demo 可超过 3 分钟，但必须另准备一个只讲定位、核心治理和指标的 3 分钟摘要版本。

### 依赖
P1/P3 必须完成；P4.7、P5 完成越多 demo 越强（缺的步骤从脚本中移除，不演示半成品）。

## S7.3 面试叙事与答辩稿

### 目标
把亮点地图（方案 §2.2）落成能开口讲的稿子：30 秒 / 3 分钟 / 10 分钟三档 + 高频追问题库。

### 对应工程点
**表达也要 eval**。稿子写完要"对抗性测试"：每个亮点自问三层追问还能不能接住。

### 改动点
- **STAR 叙事**（简历项目描述 + 开场自述用）：
  - S/T：想要一个能真正干活的个人 Agent，但裸 LLM 编数字、乱执行命令、出问题无法排查。
  - A：基于 nanobot 二开 runtime 层——防幻觉闭环 / 权限内核 / 血缘 / OTel trace / eval 回归门 / 断点恢复。
  - R：指标基线里的数据（数字一致性 100%、越权副作用/泄漏/未确认外发为 0、成本对比、恢复 demo…）。
- **三档讲法**：
  - 30 秒：方案 §1 面试版一句话。
  - 3 分钟：只讲定位、计划/权限/血缘/恢复/Subagent 与关键指标。
  - 完整版：按完整治理 demo 逐步展开。
- **追问题库**（每题写答案要点 + 对应代码承接点，方便复习）：
  - 为什么不用 LangChain/LangGraph/Dify？（own your control flow；单 agent + 确定性脚本；每层可测试）
  - 基于开源二开，哪些是你自己写的？（`nanobot/runtime/` 包 + office skill + tests；diff 统计 + 架构图分色；能逐模块讲设计取舍）
  - 注入攻击具体怎么防？防得住吗？（门控后果而非说服模型；代表性红队 smoke 经回放 CI 必跑；诚实讲未覆盖攻击面）
  - 含 LLM 的系统怎么做确定性测试？（三层：脚本单测 / 轻量 cassette agent smoke / 真模型 benchmark；cassette 失配即行为变化需要显式确认）
  - eval 为什么确定性优先？LLM judge 用在哪？（数字/权限/文件不交给 judge；judge 只评软指标）
  - checkpoint 恢复的一致性怎么保证？（completed/pending/uncertain；只有幂等键或可验证产物自动重放）
  - 上下文怎么管理？（渐进披露、offload 摘要、usage 量化）
  - 权限层为什么不一直等用户确认？（pending approval 持久化后结束执行，跨刷新/重启恢复，WebSocket 不是状态真相源）
  - Subagent 会不会成为治理盲区？（最多 5 个直接 child、禁止嵌套、权限只紧不松、预算/上下文/产物隔离、父子 span）
  - 长任务怎么保证不烂尾？（静态 plan tool 状态机 + hash 确认 + 依赖/产物核对 + 自修复 2 次失败升级人工）
  - 计划模式为什么做成静态工具？（工具 schema 进入稳定排序缓存；动态计划只在调用参数、artifact 和用户消息尾部，减少前缀失效）
  - 如果要支持多用户/上生产，还缺什么？（隔离、鉴权、配额、trace 采样——说明知道个人项目与生产的差距）
- 每个回答标注"证据位置"（文件/指标/测试），确保追问时能落到实处。

### 实施步骤
1. 对照方案 §2.2 逐行写答案要点。
2. 自我模拟面试（或找同学互问），把接不住的追问补进题库或补进工程。
3. 简历措辞终稿：只写已完成 + 有指标的能力，每条尽量带数字。

### 验收
- §2.2 每一行都有 30 秒版答案 + 三层追问应对。
- 简历项目描述 ≤4 行，每行有量化支撑。

### 依赖
S7.1（数据）、S7.2（demo）；随各阶段完成持续更新。
