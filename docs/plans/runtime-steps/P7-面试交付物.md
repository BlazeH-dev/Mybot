> 状态：P7 代码交付与 README 最终结果页已完成（2026-07-24）；日本区 Cloud、Luna、Terra Connection/Judge、licensed Dataset 与 token 估算已验证。首个真实 Run 因 OCB 转换资产缺失停止；完整质量结果、PresentBench media、人工审核和发布数字仍未完成。

## 1. 一键入口

```bash
nanobot benchmark prepare --profile office-smoke
nanobot benchmark prepare --profile office-release
nanobot benchmark estimate --profile office-release --model-preset gpt-5-6-luna
nanobot benchmark run --profile ci
nanobot benchmark run --profile office-smoke --model-preset gpt-5-6-luna
nanobot benchmark run --profile office-release --model-preset gpt-5-6-luna --presentbench-sample 60
nanobot benchmark export --dataset-run <langfuse-dataset-run-id>
```

- `ci`：deterministic eval、cassette、代表性红队和 adapter contract；无 API Key、无网络、不开 Langfuse。
- `prepare`：准备外部 Office 资产和独立 benchmark venv，校验 revision/SHA/license，并创建/校验不可变 Langfuse Dataset；不创建本地 Dataset CRUD。
- `estimate`：在调用模型前按 Agent/Judge input/output 给出 full/50%/25% token 规模；实际 token 由 Langfuse generation 统计。
- `run`：薄封装 Langfuse Python SDK `run_experiment()`，task callback 执行 Luna Agent 和对应 Skill；并发、Trace、错误隔离、Dataset Run、item/run evaluator 与 Score 均由 SDK/Langfuse 管理。
- `export`：只读取一个已完成且审核齐全的 Langfuse Dataset Run，生成去敏结果快照和 README 受控区块。

当前实现已提供 `README.md` Mermaid 架构图、无 Key CI quickstart、Langfuse 日本区配置说明和受控 benchmark 区块。真实 run 未完成前结果区块明确显示“尚未发布”，不填估算值或占位 deep link。

换电脑时，P7 仍须从 P5 runbook 的“每台新电脑/新工作区必做”部分开始：重新准备 Python/Node 依赖、`~/.nanobot/config.json`、稳定 LibreOffice、benchmark venv/cache，运行离线 `ci` 和 redacted Cloud preflight；需要重新生成 OCB PDF 转 Office 资产时，还要从密码管理器向当前 shell 注入 Adobe PDF Services 凭据。日本区 Project、Terra Connection/Judge、Dataset/Run/Queue 属于 Project 或实验记录，可在新机器复用；只有 Key/区域/模型、revision/license、Judge 配置或数据策略变化时才重建。P7 的真实结果链接和导出快照不因换机自动失效，但新机器不能把旧 cache 当作本地环境证据。

删除 `benchmark status/resume/audit-sync/publish`、单 active run 锁、本地 run/score 状态机和 benchmark WebUI。运行进度、失败 case、Score、token 和人工审核直接在 Langfuse 查看；失败 case 首版以带 `parent_run_id` 的 retry Dataset Run 重跑，不自建断点恢复。

`office-smoke` 固定三套 benchmark 各 4 个 case、两个 Skill 同题，12 个 case 产生 24 个 experiment traces，全部进入 Annotation Queue。`office-release` 跑 OCB 全量、固定 OfficeBench Office subset，PresentBench 在三档 token 估算后选择独立 Dataset/series。两者都要求外部预装且版本锁定的 LibreOffice，以及日本区 Cloud 写入、flush、API 回读和 deep link smoke。

## 2. 评估与结果归属

| 内容 | 执行位置 | 唯一记录位置 |
| --- | --- | --- |
| deterministic/cassette/Policy/OCC/HITL/恢复 | 本地 pytest/CI | CI 结果与 committed deterministic snapshot |
| OfficeBench 官方 evaluator | Experiment Runner 进程中的 SDK evaluator | Langfuse `official_score` |
| OpenXML/渲染/文件 hard gate | Experiment Runner 进程中的 SDK evaluator | Langfuse item Score；代码回归仍由本地 CI 判定 |
| OCB Terra Judge | Langfuse Custom LLM-as-a-Judge | Langfuse `mybot_score` + reasoning |
| PresentBench 内容/视觉 Judge | Langfuse Custom LLM-as-a-Judge；视觉不支持时仅该维度本地 SDK evaluator | Langfuse `mybot_score` + reasoning |
| 人工审计 | Langfuse Annotation Queue | Langfuse Score/comment/reviewer |
| Token、延迟、成功率、趋势 | Langfuse generation/Dashboard | Langfuse |

OCB/PresentBench 使用 Langfuse LLM Connection 连接 OpenAI-compatible 的 `gpt-5-6-terra`，仍标记 `Mybot evaluation`，不能称为官方分数或 `official-comparable`。三套结果不合成总分；报告必须分别给出 `supported/total`、`passed/total`、`passed/supported`，unsupported 的 token 和耗时单列。

Git 中只保留发布快照：

```text
benchmarks/latest.md                 结果类型和 Langfuse deep link 索引
benchmarks/runtime/latest.{json,md} deterministic/fake-provider 证据
benchmarks/office/latest.{json,md}  从已审核 Dataset Run 导出的真模型结果
benchmarks/exports/<run-id>.json     去敏、不可编辑的 Langfuse 导出快照
```

原始 benchmark 数据、完整 Trace、Office 文件和不能上传的渲染媒体保存在外部缓存。Score、Judge reasoning、人工审核和跨 run 趋势不复制进本地数据库；导出快照只服务 Git/README 展示。

## 3. Office Skill 对比

P1.1 已完成；对 `officecli` 与 `office-python` 分别运行同一个 Langfuse Dataset 和 evaluator config：

- capability coverage：`supported/unsupported/passed/failed`；
- common-task quality：OfficeBench official 或 OCB/PresentBench Mybot score、人工 Score、Token、LLM/tool latency、tool success 和 Agent steps；
- 使用 Dataset Run comparison、Score Analytics 和 Dashboard 查看差异，不在 Mybot 重做跨 run 图表；
- OCB 证明文件理解，OfficeBench Office subset 证明 Word/Excel 创建编辑，PresentBench 证明 PPT 创建和视觉质量。

OfficePython 是公平 Python baseline，不得通过 Dataset、prompt 或 evaluator 配置偏袒 OfficeCLI。

## 4. Langfuse 与 Mybot UI

Langfuse 固定使用日本区 Cloud `https://jp.cloud.langfuse.com`：

- Python SDK 随 Mybot 默认安装并锁定版本（`langfuse>=4.14.0`），负责 OTel observation、masking、batch/retry/flush、Experiment Runner 和 Scores API。
- Langfuse UI负责 Trace/Sessions、Datasets/Dataset Runs、Experiments、Scores、token/延迟 Dashboard、Monitors、Annotation Queue 和失败下钻。
- Mybot 不建 Trace 查询、Dataset/Experiment CRUD、benchmark 状态面板、Score 管理、跨 run 图表或标注 UI；WebUI 只保留当前 Runtime 的 plan/approval/artifact/checkpoint，并提供 Langfuse deep link。
- `observability.langfuse.enabled=false`（默认）时保留现有 JSONL TraceHook 作为本地调试路径；启用后切换到 Langfuse SDK 并停写 JSONL，二者互斥。Cloud 关闭或故障不阻塞普通 Runtime；smoke/release 把 Cloud preflight 作为硬门。
- `langfuse.openai` drop-in 在 provider 从 config 设置环境变量后自动追踪 OpenAI/DeepSeek/GPT-5.6 的所有 LLM 调用；`runner._request_model()` 和 `runner._run_tool()` 逐调用创建 generation/tool observation。
- LLM Connection 中保存 Terra 中转站 Key/Base URL；Mybot 只保存 Langfuse SDK 项目 Key。两类密钥都不得进入前端、仓库、导出快照或 Trace。
- 只上传许可证允许且已脱敏的 metadata/rubric/media；公司或敏感内容在合规审查前关闭 Cloud。
- Cloud 模式不要求本机安装 Redis、MinIO、ClickHouse 或 PostgreSQL。

## 6. 用户配置与最终交付步骤

完整字段、JSON、命令、预期结果和停止条件以 [P5.1 用户配置与真实运行步骤](./P5-trace-eval.md#p51-用户配置与真实运行步骤必须按顺序) 为唯一操作 runbook。P7 按以下顺序验收交付，不允许跳步：

| 顺序 | 用户动作 | P7 可核对证据 | 未通过时的状态 |
| --- | --- | --- | --- |
| 1 | 运行无 Key `nanobot benchmark run --profile ci` | 当前预期 `54 passed` | Runtime 基线失败，不启动 Cloud |
| 2 | 配置 `providers.openai.apiKey/apiBase`，确认 Luna 实际模型 `gpt-5.6-luna` 可调用 | Mybot Provider 可执行真实 Agent task | 不运行 benchmark |
| 3 | 在 `https://jp.cloud.langfuse.com` 创建专用 Project，配置 Project Public/Secret Key；先保持 `captureContent=false` | metadata-only Cloud smoke 可写入、flush、API 回读并打开 deep link；本轮已验证 | preflight 失败时不运行真模型 |
| 4 | 安装稳定版 LibreOffice，确认 Luna/Terra token 统计口径，完成公开数据许可和跨境上传审查 | 精确 `soffice --version`、分项 token 估算、审查记录 | 只能 redacted prepare，不能真模型运行 |
| 5 | 在 Langfuse 创建 `gpt-5.6-terra` OpenAI-compatible LLM Connection，以及只作用于 OCB/PresentBench 的两个 100% Judge；Score 名固定 `mybot_score` | 本轮已验证 Connection `mybot-terra-judge-v1`、evaluator `mybot_score` v1 和两条启用规则 | 配置漂移或测试失败时 OCB/PresentBench 不可导出 |
| 6 | 临时设置 `captureContent=true`，用 `--allow-licensed-content` 重新 prepare `office-smoke`，再 estimate 并核对 token 规模；缺失 OCB 转换资产时向当前 shell 注入 Adobe PDF Services 凭据后重跑 prepare | 三个 `licensed-v1` Dataset、schema v2 prepared fingerprint、四个 OCB 引用文件/摘要和分项 token 输出 | 资产或 token 规模异常时先修复，不调用模型 |
| 7 | 运行 `office-smoke`；先用 `--benchmark ocb --skill officecli --parent-run-id 8e63bb66-f505-4e08-b16a-70399467e074` 恢复失败组合，再用过滤参数运行其余五组 | 6 个成功 Dataset Run、6 Queue、24 条成功 traces；失败父 Run 只作基础设施证据 | 失败组合使用独立 retry Run；不修改或发布原 Run |
| 8 | 验证 PresentBench rubric/media 真正进入 Judge；在六个 Queue 审核全部 24 traces，填写 `mybot-human-review` 并完成 item | OCB/PresentBench `mybot_score`、OfficeBench `official_score`、人工 Score/comment/reviewer | media/Score/审核任一缺失时不发布对应结果 |
| 9 | 对每个已审核 Dataset Run 分别执行 `benchmark export --dataset-run <id>`；最后导出要在 README 展示的 Run | `benchmarks/exports/<run-id>.{json,md}`、README 真实 deep link | export 失败时禁止手工填数字或链接 |
| 10 | 恢复 `captureContent=false`，按需关闭 `enabled` 并重启 gateway；smoke 全部通过后才以相同档位执行 release prepare/estimate/run/review/export | 安全默认值恢复、release snapshot 与提交记录 | 仍保留“外部证据待配置/未发布”状态 |

三套 Key 的责任必须分开：Luna Key 在 Mybot Provider 配置，Langfuse Project Key 在 Mybot observability 配置，Terra Key 在 Langfuse LLM Connection。任何 Key 都不得进入 README、Git 导出、截图或 Trace。当前机器已锁定 `/Applications/LibreOffice.app/Contents/MacOS/soffice`，完整版本为 `LibreOffice 26.2.4.2 0229ac93fcf0d7cbc6376066c6f35021cef002dc`；Codex runtime 中的 LibreOfficeDev 仍不是稳定 release 证据。

P7 的“真实结果已发布”必须同时满足：日本区 deep link 可访问、Run item 完整、必需机器 Score 齐全、Queue 审核达标、导出无敏感内容、README 由 CLI 更新且对应已提交 Git SHA。只完成账号/Key 配置、只看到 Trace、只跑 estimate 或只完成人工 Queue 都不算闭环。
