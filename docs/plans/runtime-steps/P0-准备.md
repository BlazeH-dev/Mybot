## S0.1 固定 fixture（标准输入与期望值）

### 目标
准备一份最小但真实的 Office 任务输入，以及人工核对过的期望指标 / 约束，作为两个独立 Office Skill 和后续 Runtime 治理的共同回归基准。

### 对应 harness 工程点
**Eval 数据集 / Golden fixture**。成熟 Agent harness 的第一块基石不是模型，而是"可重复的评测样本"。固定 fixture = 让后续每一步都能确定性验收（而不是靠人眼看输出"差不多对"）。对应方案 §14.10、§15.4。

### 改动点（新增文件，无代码逻辑改动）
- `tests/fixtures/office_weekly/sales_data.xlsx` — 销售明细，含可聚合字段（如 `date / region / gmv / orders`）。
- `tests/fixtures/office_weekly/meeting_notes.md` — 一段会议纪要（含结论、风险、行动项各 1–2 条）。
- `tests/fixtures/office_weekly/expected_metrics.json` — 人工算出的期望指标（GMV 合计、订单量、转化率、Top 区域…）。
- `tests/fixtures/office_weekly/expected_constraints.json` — 任务约束（如 `pptx_max_pages: 6`、`must_include: ["GMV","订单量","转化率"]`）。
- `tests/fixtures/office_weekly/make_fixture.py` — 一次性生成 xlsx 的脚本（用 `openpyxl`），便于日后复算/调整数据。
- `tests/fixtures/office_weekly/test_fixture.py` — fixture 自检测试，供 P0 CI smoke 直接复用。

### 实施步骤
1. 设计最小数据表结构（5–10 行足矣，覆盖"多区域、可求和、可算比率"）。
2. 写 `make_fixture.py` 用 `openpyxl` 生成 `sales_data.xlsx`（把数据写死在脚本里，保证可复现）。
3. 手算指标，落到 `expected_metrics.json`（每个指标记 `value` 与 `display_value`）。
4. 写 `meeting_notes.md`，确保含"结论/风险/行动项"三类内容（后续 meeting_coverage 指标要用）。
5. 写 `expected_constraints.json`。
6. 写 `test_fixture.py`，把 workbook 汇总值与期望 JSON 做确定性比对。
7. 运行 `make_fixture.py`，确认 xlsx 能被 `openpyxl` 重新打开。

### 验收
- 6 个文件齐全；`openpyxl.load_workbook(sales_data.xlsx)` 成功。
- `expected_metrics.json` 的数值可由 xlsx 手算复核（你自己核对一遍）。
- Python Skill 与 OfficeCLI Skill 都引用同一输入和 expected metrics；输出结构可不同，数字硬门相同。
- `pytest tests/fixtures/office_weekly/test_fixture.py -q` 通过。

### 注意
- 数值故意"好算"（整数、便于求和），降低后续比对的浮点误差噪声。
- 不要把 xlsx 当二进制硬塞进 git diff——保留 `make_fixture.py` 才是可维护的做法。

### 依赖
无（起点）。

## S0.2 真 CI：GitHub Actions 回归门【2026-07-06 新增】

### 目标
把方案通篇引用的"CI 回归门"从口头承诺变成公开可见的 pipeline 实体。

### 对应 harness 工程点
**Agent CI**。方案 §2.2 / §4.6 反复讲"改动即回归"，但项目目前没有任何 CI 配置——面试官追问"你的回归门在哪"时，答案应该是一个绿色徽章链接，而不是一段解释。P0 就建的原因：测试随各阶段增长，CI 自动跟着长，还能持续产出"回归耗时 < 60s"这条基线指标；等 P5 再补就白白少攒两个月的公开运行记录。

### 改动点
- `.github/workflows/ci.yml`：push/PR 触发，跑 `ruff check nanobot/` + 确定性 pytest smoke（P0 fixture + 模型/命令/settings 核心用例；S5.0 完成后轻量 cassette smoke 自动纳入）。
- README 挂 CI 徽章（P7 时随 README 一起完善即可，workflow 先建）。
- 注意：上游 tests 体量大，若全量跑超时/有环境依赖失败，先用 marker 圈定"二开相关 + 上游核心"子集，并在 workflow 注释里写明取舍。

### 实施步骤
1. 写 workflow（Python 3.11 + 安装依赖 + ruff + pytest）。
2. 推一次验证绿；失败则圈定测试子集。
3. 记录首次"回归耗时"进指标基线。

### 验收
- GitHub Actions 页面可见绿色运行记录；后续每个阶段的提交都自动带回归。
- 本地全量 `pytest tests/ -q` 首次摸底为 `142 failed, 3910 passed, 3 skipped`，失败集中在网络下载、API key、端口/HTTP 服务和 home 目录写入等旧环境依赖；P0 CI 已按本节备注先圈定确定性 smoke，后续阶段逐步扩大。

### 依赖
无（可与 S0.1 并行；半天内完成）。
